# 镜像插件化重构契约

> 本文是 2026-08-23 开始的镜像、沙箱组合和实验/竞赛运行时重构的最终收敛契约。它补充并细化 `docs/总-镜像与容器设计.md`、`docs/02-沙箱引擎/`、`docs/07-实验/` 和 `docs/08-竞赛/` 中的实现边界。若旧实现、旧字段或旧注释与本文冲突，以本文为准；旧兼容路径必须删除，不得继续双写。

## 1. 镜像到底是什么

镜像是一个不可变、可验证、可部署的原子能力单元，不是实验包、竞赛包，也不是固定组合矩阵中的一个格子。

| 类别 | 运行期角色 | 是否进入教师组合选择器 |
| --- | --- | --- |
| `runtime` | 提供一条具体链实例及其 RPC、peer、REST、账本和原生动作能力 | 是，可在一个环境中选择多个实例 |
| `infra` | 提供链下设施或协同服务 | 是，或由 `requires` 自动展开 |
| `tool` | 提供学生或教师使用的工具能力 | 是，必须显式选择 |
| `judger` | M3 私有判题能力 | 否，由平台/判题器专用流程选择 |
| `base` | 仅用于构建其他镜像 | 否，不能成为沙箱 sidecar 或学生入口 |
| `service`/`middleware`/`network` | 平台自身基础设施 | 否，不进入普通沙箱组合 |

镜像提供能力，`CompositionSpec` 决定组合。不能因为两个镜像都有相同 `eco_tags` 就认为它们可组合；也不能因为某个运行时存在就隐式注入工具。

镜像准入与组合可用性是两个独立判定：镜像通过 manifest、不可变 digest、供应链安全、自检和基础 WorkloadSpec 门禁后进入平台目录；组合编译再按该镜像的 `requires`、端点、参数、Secret 和 `links` 判断当前环境是否闭包。组合不满足条件时只拒绝当前组合并返回缺失能力或连接，不能把非安全问题写成 `supply_chain.deployable=false`，也不能因此把镜像从目录删除。

## 2. Runtime 插件契约

每个 runtime 插件必须在自身最终镜像内提供 manifest 声明的节点进程、端点和基础自检所需文件。需要平台原生链动作时，才额外声明 `runtime.native.helper`；该路径必须在最终镜像中存在，`exec_target` 必须指向一个已声明且非学生入口的容器。学生文件与终端能力由 M2 生成的 runtime 适配器统一声明为平台私有的 `tool/workspace` sidecar，并随每个实际 runtime 实例进入组合快照闭包；它不是教师可选工具，也不是 `base/chain-tools` 的运行时注入。若未来某个 runtime 需要不同的工作区实现，必须由该 runtime 适配器显式声明自己的私有 sidecar，不能在编排器中按生态或镜像名分支。

平台只依赖统一的 stdin/stdout JSON 协议：`deploy`、`tx`、`query` 和声明的 `reset`/`recreate_runtime`。`adapter_level: 2/3` 的 runtime manifest 必须为三个标准动作分别声明 `native.actions` 或 `native.methods`,并提供 `capability_selftest.deploy_payload` 与 `capability_selftest.query_target`;只声明版本探活且没有 manifest 声明的真实节点端点/基础自检的镜像才保持 `onboarding`,不能进入可编排目录。`adapter_level: 1` runtime 只要真实提供 manifest 声明的 RPC、peer 或 REST 基础能力,即可作为组合能力提供者进入目录,不开放未声明的原生动作。runtime manifest 的 `native.actions` 声明动作 argv,`native.methods` 声明 RPC 方法；平台只做边界校验和环境注入,不解释这些值。生态差异属于 runtime 插件自身；平台后端不得按 `eco` 维护适配器 `switch`,不得把一个中心化万能 helper 当作所有生态的实现。

`base/chain-tools` 可以继续作为构建基座或平台私有构建输入，但不得被注入为 `student-shell`、`chain-adapter` 或其他运行期组件。终端连接默认复用平台受控 exec/PTY；终端所依赖的文件操作 helper 可以由 runtime 的私有 workspace sidecar 提供，但必须在组合快照中作为实际镜像闭包登记，不能通过 base 镜像隐式提供。

运行时镜像的状态必须拆成三层，不能用一个字段混淆：

1. **镜像准入**：manifest、不可变 digest、供应链安全、基础自检和 WorkloadSpec 完整后，镜像进入平台目录。这个门禁对 `runtime`、`infra`、`tool`、`judger` 使用同一原则；只有明确安全/供应链阻断才禁止部署。
2. **组合准入**：组合编译器按 `provides/requires/conflicts/cardinality/placement`、端点、参数、Secret、连接和资源闭包判断一个镜像能否参与当前实验或竞赛。缺少依赖只拒绝当前组合，不能把镜像标成安全不可部署。
3. **运行时动作准入**：`adapter_level: 1` 只表示该 runtime 已能启动节点并提供 manifest 声明的基础能力（例如 RPC、peer、REST）；它可以作为环境中的节点/能力提供者参与组合，但不能被调用平台原生 `deploy`、`tx`、`query`。`adapter_level: 2/3` 只有在自身 helper、动作自检和真实下游闭环完成后，才开放这些动作。动作未闭合不影响该镜像作为其他组件依赖的节点或服务使用。

因此，L1 runtime 不是“不能进入实验/竞赛”，而是“作为基础能力提供者参与组合，但不能被调用未声明的原生链动作”。例如区块浏览器、事件监听器、索引器、钱包或教学工具只要声明需要的 RPC/服务能力并通过命名绑定连接，就可以和 L1 runtime 一起部署；只有题目初始化、自动判题或工作流明确调用 `deploy`/`tx`/`query` 时，编译器才返回动作能力缺失。目录、前端选择器和组合编译器必须分别展示这三层状态，不能再把 L1 统一隐藏。

当前 runtime 目录的真实状态：`runtime/evm-foundry`、`runtime/edu-chain`、`runtime/evm-geth` 和 `runtime/evm-hardhat` 已声明各自镜像内的原生 `deploy`/`tx`/`query` helper 及能力自检。Foundry 已有正式 digest 的 Docker/Kubernetes 闭环；Edu、Geth、Hardhat 已完成当前候选 digest 的 Docker 闭环和 Kubernetes 多镜像闭环，但候选 digest 尚未完成 Trivy、SBOM、Cosign 证明，因此仍不得标记为最终可用或写入正式 digest 锁。`runtime/bitcoin` 已完成候选 digest `sha256:9c7e7ef94d20267654989af37f3667d384fb456e53a1130120022eb308ca11ad` 的 Docker 和 Kubernetes Service/DNS、真实 OP_RETURN、UTXO 交易、链查询闭环，进入候选 L2；它仍需完成正式供应链证明后才能进入可编排目录。`runtime/cosmos`、`runtime/evm-besu`、`runtime/fabric`、`runtime/fisco-bcos`、`runtime/move-aptos`、`runtime/move-sui`、`runtime/near`、`runtime/solana`、`runtime/substrate` 保持 `adapter_level: 1` 的基础组合能力：本轮已完成当前镜像的启动或基础 RPC/节点验证，但尚未提供平台原生动作闭环；它们仍可作为 RPC、peer、REST 等基础能力提供者参与组合。FISCO 的 `CHAIMIR_FISCO_CONFIG` 由 M2 生成并验证运行期 `config.ini`,缺少该配置时只拒绝当前组合,不阻断镜像目录准入。每个运行时完成自己的原生 helper、能力自检、镜像证明和真实下游闭环后，才单独提升动作等级。

### 2.2 运行时准入修复门槛

只有要把某个 `adapter_level: 1` runtime 提升为“可调用平台原生链动作”时，才必须按该镜像自己的生态协议补齐原生 helper 和 manifest 能力声明，不能只修改等级或在平台后端增加生态分支。L1 的基础节点/RPC 能力仍必须先通过镜像和 WorkloadSpec 门禁，随后即可作为可组合能力提供者使用。提升动作等级至少要有以下可复现证据：

1. 镜像内 helper 真实完成 `deploy`、`tx`、`query`，以及声明的 reset 策略；不接受固定成功值、假交易哈希或仅版本探活。
2. Docker 冒烟通过后，在组合快照中完成运行时启动、依赖 Service/DNS 解析、核心动作和回收；工具通过显式 `links` 观察运行时状态时，必须验证源动作确实改变目标可见状态。
3. 重新构建并按不可变 digest 推送，完成 Trivy、SBOM、Cosign 签名与验证，生成候选锁；候选锁只有在正式证明通过后才能晋升到 `images/image-digests.lock` 和平台 attestation。
4. 只要任一动作或组合门槛未完成，只关闭受影响的动作或当前组合，并在自检详情中记录具体阻塞阶段；只有镜像安全/供应链门禁失败才标记为不可部署。不得用本地 tag、旧 digest 或手工 attestation 冒充准入。

### 2.3 本轮运行时与平台镜像分类结论

本轮复核对象不能混用同一套准入标准：

| 对象 | manifest 类别 | 正确能力边界 | 当前处理结论 |
| --- | --- | --- | --- |
| Bitcoin、Cosmos、Besu、Fabric、FISCO-Bcos、Aptos、Sui、NEAR、Solana、Substrate | `runtime` | 一条具体链实例的节点、RPC/peer/REST 等 manifest 声明的基础能力，以及该生态自己的原生动作 | 镜像和基础 WorkloadSpec 通过后即可作为满足依赖的链能力提供者；只有真实 `deploy`/`tx`/`query`/reset 闭环才能开放平台原生动作 |
| Chainlink | `infra` | 预言机/VRF/Automation 链下设施，通过组合 `links` 连接主 runtime | 不执行 runtime 动作；当前阻塞是上游二进制漏洞，不能用改 adapter 等方式绕过 |
| The Graph、IPFS、Postgres Graph | `infra` | 索引与内容寻址协同设施，通过 `requires` 自动展开并由 `links` 注入 RPC、数据库和存储地址 | 不执行 runtime 动作；必须按各自原生配置和真实依赖闭环验证，不能只凭 GraphQL/端口探活 |
| bridge-relayer | `infra` | 跨链中继协同设施，需要多个 runtime 实例的 RPC、链配置和签名材料 | 镜像本身可进入目录；组合必须提供多 runtime 实例连接闭包，缺少时由编译器拒绝该组合，不得按单链工具隐式调度 |
| Harbor | `middleware` | 平台镜像仓库和扫描服务，不属于沙箱组合 | 不执行 runtime 动作；官方组件集存在未修复漏洞时保持不可部署 |
| Grafana | `observability` | 外接监控看板，只读嵌入到管理端 | 不执行 runtime 动作；当前 Wolfi 修复包未满足扫描门槛时保持不可部署 |

`deploy` 的含义由 runtime 插件自己定义，不能把没有原生部署语义的链强行包装成合约链：Bitcoin 可将部署动作定义为真实 OP_RETURN 发布并确认交易；Cosmos 当前 Gaia 镜像没有 CosmWasm 合约模块，Substrate 当前 Polkadot 开发链没有合约部署 pallet，这两者保持 L1 基础链能力,只有更换为具备相应模块的运行时实现并完成闭环后才能升 L2；FISCO-Bcos 在 M2 生成并验证节点配置前只拒绝需要该配置的当前组合。Fabric、Aptos、Sui、NEAR、Solana 和 Besu 只有在其真实账户、签名、包/程序部署和状态查询链路闭合后才能提升，不能以版本探活或外部工具代替 runtime 原生能力。

### 2.1 生产运行时接入即测

镜像没有本地/生产两套接入语义。所有验证都使用正式不可变 digest,在目标 Kubernetes 运行时执行：控制面通过 `POST /api/v1/sandbox/runtimes/{id}/selftest` 创建隔离沙箱,按 runtime manifest 的声明执行 `start/selftest -> deploy -> tx(若声明) -> query -> reset`,随后回收沙箱并持久化结果。该接口是运行时接入即测的唯一入口,不接受本地 tag、`latest`、宿主机源码挂载或旧缓存作为证据。

运行时自检通过只表示镜像内声明的进程和适配器在目标 Kubernetes 中完成了声明的闭环;仍必须通过镜像证明、完整镜像闭包预拉取、NetworkPolicy/资源限制、核心动作和回收验证,全部满足后才允许标记 `available`。

2026-08-24 当前证据：`runtime/edu-chain`、`runtime/evm-foundry`、`runtime/evm-geth` 和 `runtime/evm-hardhat` 已使用当前镜像完成 `selftest -> deploy -> tx -> query -> reset`；Foundry 与 `tool/contract-ui` 已在独立 Docker 网络中通过服务名完成真实 JSON-RPC 查询、合约 calldata 交互和交易回执验证。当前 `docker-desktop` 六个节点已修复 canonical Harbor split-DNS，并按正式 robot pull Secret 从 Harbor 按 digest 拉回候选镜像。候选 Kubernetes 组合 `chaimir-image-e2e` 已验证 `edu-chain` (`sha256:c7aad4d0d929d38b385ae47496cbb5e579c1ceafcea506bffdd3899bd9b0953f`)、`evm-geth` (`sha256:56b4a7c8b879485fce52870ebfc82a4b9db9d8db96f6200bf75acba837bb8c84`)、`evm-hardhat` (`sha256:453b48dd9d4497f251c23bf6fe85c6829b837930c6c73e0e765ba2331b5023dd`) 与正式 `tool/contract-ui` digest 的 Pod 就绪、Service DNS 查询、helper 的 deploy/tx/query，以及工具观察运行时状态；Geth 入口还修复了 Kubernetes `GETH_PORT` Service 注入冲突。上述 digest 仍属于候选证明，未完成 Trivy、SBOM、Cosign 签名验证前，不得标记为最终可用，也不得写入正式 digest 锁或平台 attestation。

## 3. Manifest 单一真相源

runtime、infra、tool、judger 的 manifest 必须使用同一套结构化能力模型：

`provides`、`requires`、`conflicts`、`cardinality`、`placement`、`config_schema`、`student_access`。

manifest 还必须完整声明最终 workload 所需的镜像 digest、版本、组件名称、启动命令、探针、自检命令、端口、环境变量名、Secret 引用、资源、安全上下文、临时目录和挂载安全域。seed 只做 schema 校验和规范化，不得丢弃这些字段后在后端按生态补写。

`infra` 与 `tool` 使用同一份能力和连接契约。`capabilities.requires/conflicts/cardinality/placement/config_schema/student_access` 必须原样进入 M2 的 WorkloadSpec，不能只保存 `provides`。需要其他组件端点的镜像必须声明结构化 `bindings`，每个绑定包含稳定角色名、所需能力、目标端点、协议、是否启动前置和 `config_binding`；绑定只能依赖能力和端点，不能写死 runtime code、镜像名或生态组合。组件能通过 TCP/HTTP 探活，不代表语义兼容；例如 EVM 事件监听、区块浏览器、ERC-4337 bundler/paymaster 只能要求 `evm-json-rpc`，不能用 `eco_tags` 或通用 `rpc` 端口替代。

多链组件必须使用多个命名绑定表达角色，而不是声明一个模糊的 RPC 环境变量。例如跨链中继可以声明 `source_chain` 和 `destination_chain` 两个绑定，二者都要求 `evm-json-rpc`，分别指向所选 runtime 实例的 `rpc` 端点；编译器根据能力、端点、冲突和组合参数解析提供者，并把两个 Service/DNS 地址分别注入源链和目标链配置。没有满足任一绑定时，只拒绝当前组合，不阻断该镜像的目录准入。

镜像 manifest 中的绑定使用以下固定结构；`bindings` 位于镜像类别节点（`infra`、`tool` 或 `judger`）下，旧的 `required_bindings` 不再存在：

```yaml
bindings:
  - name: source_chain
    capability: evm-json-rpc
    endpoint: rpc
    protocol: HTTP
    required_at_start: true
    config_binding: env:HYP_SOURCE_RPC
```

`name` 是组件内稳定角色名，同一 manifest 不得重复；`capability` 和 `endpoint` 只引用提供者的结构化能力与端点；`protocol` 只允许 `TCP`、`HTTP`、`HTTPS`、`WS`、`WSS` 或 `GRPC`；`required_at_start` 决定启动等待与 NetworkPolicy 生效顺序；`config_binding` 当前只允许 `env:ENV_NAME`，其中 `ENV_NAME` 必须同时出现在该 manifest 的 `env_keys.config`，不得写固定 Service/DNS、镜像名或 runtime code。需要文件、Secret 或多个字段的协议配置必须由组件自己的入口读取平台生成的受控配置挂载，并在 manifest 中显式声明对应 mount/secret，不得把多个角色压缩成一个环境变量。

`postgres-compatible` 是数据库能力契约,不是固定镜像名。提供者必须声明 `postgres` TCP 端点并在组合参数中接受数据库名、用户和平台 Secret；消费者必须通过 TCP binding 获取 `ServiceDNS:5432` 形式地址,在自己的入口中生成官方 PostgreSQL URL,不得把原始地址直接当作 URL 或把 `middleware/postgres`、`infra/postgres-graph` 写死为依赖。消费者若需要密码,必须在 `env_keys.secret`/`secrets_required` 中声明同名 Secret,缺少凭据时入口拒绝启动。

组合声明必须支持多个 runtime 实例。runtime 实例使用组合内稳定的组件编码或实例别名区分，不能把第二条链塞进 infra/tool 或通过重复 `primary_runtime` 字段兼容。`workspace_runtime_instance` 必须显式指定承载工作区、初始化和学生文件入口的 runtime 实例；平台不得按数组顺序或字典序选择工作区运行时。跨链 relayer、跨链监听、双链判题等组件必须通过命名绑定连接多个 runtime；镜像只要通过自身安全/供应链门禁，就应进入镜像目录，由组合编译器在缺少所需链实例、端点或 Secret 时返回明确的组合错误。

组件需要密钥时只能声明 `secret_env` 引用，M2 在创建沙箱前把声明键从平台受控 Secret 同步到当前命名空间，再由 Kubernetes `SecretKeyRef` 注入；组合参数和连接地址仍分别来自声明参数与 `links`。`capabilities.config_schema.properties.<param>.x-chaimir-env` 是唯一的非敏感参数映射，值使用 `组件名/ENV_NAME`；单组件时也可以只写 `ENV_NAME`。编译器必须把 `CompositionComponentRef.params` 按该映射写入对应组件的字面量环境变量，并拒绝未声明映射、映射到 `secret_env` 或与 `links` 产生不同值的参数。禁止把密钥写入 `env.value`、镜像、组合 JSON 或宿主机文件，也禁止因为容器可以启动就省略必需 Secret 的就绪校验。

判题器额外在 `judger` 节声明 `runtime_code`、`genesis_ref`、非 shell `command`、受控 `exec_target`、字面量环境变量和 `suite_archive_name`；超时来自 `resources.timeout_seconds`。迁移层不得按判题器名称推断链、命令、脚本或安全策略。

生产镜像的最终地址和 digest 只能来自已验证的不可变证明清单；manifest 中的上游 digest、CI 生成的 `images/image-digests.lock` 和部署 attestation 必须经过同一校验器确认，不能形成三套互相漂移的真相源。

runtime 版本必须来自 manifest 的明确发布版本或 digest 派生版本，禁止使用全平台硬编码日期字符串。runtime/tool/infra 的目录主键必须按稳定 code 生成或由数据库序列产生，禁止依赖目录枚举顺序。

## 4. 唯一组合编译器

实验、解题赛、对抗赛、漏洞预验证和私有判题均调用 M2 的唯一 `CompositionSpec` 编译器。编译器执行：

1. 校验一个或多个 runtime 实例、显式 infra、显式 tool、参数和连接图。
2. 按 `requires` 展开依赖，检测循环、冲突、基数、placement、端口、安全域和访问配置。
3. 使用确定性的 provider 选择策略；存在多个同等 provider 时必须要求显式选择或返回歧义错误，不能取字典序第一个。
4. 将 `required_at_start` 编译为启动依赖和健康等待顺序。
5. 生成不可变 `composition_snapshot` 和 `composition_digest`。

同一组合中多个 runtime 若声明同名安全域，必须使用完全一致的挂载、访问、持久化和快照契约；否则只拒绝当前组合。共享工作区的容器路径始终来自显式 `workspace_runtime_instance`，不能从 runtime 数组顺序推断。

`eco_tags` 只能用于目录筛选和展示，不参与最终兼容判定。不存在固定 N×M 组合表、运行时默认工具、旧字段双写或业务模块自建组合器。

## 5. 完整镜像闭包与预拉取

已发布快照的 `image_closure` 必须包含实际启动会用到的全部镜像：

- 每个 runtime 实例的镜像；
- runtime manifest 声明的 infra sidecar、init 和私有适配器镜像；
- 显式选择及依赖自动展开的 infra/tool 组件及其 init/sidecar 镜像；
- 每个镜像对应的不可变 digest、版本、预拉取命令、保持用途和临时挂载。

`ImageClosureItem` 同时冻结 `prepull_command`、`prepull_hold` 和 `ephemeral_mounts`;预拉取服务必须按快照逐项比对这些字段，不能只比较 URL 后重新解释当前目录。

预拉取状态必须按 `(runtime_image_id, composition_digest)` 唯一标识,由 `sandbox_composition_prepull` 保存状态、尝试 ID、DaemonSet、镜像列表、节点进度和失败原因；`runtime_image` 不承载组合级预拉取状态。

预拉取 API 必须显式接收已发布 `composition_digest`。预拉取、启动、恢复、工具挂载和回收只能引用该摘要对应的快照，禁止根据当前生态标签重新计算闭包。

## 6. 发布和生命周期

M5 发布实验/题目时必须锁定每个环境的组合快照；M7/M8 起环境只能使用锁定快照，禁止在启动时重新编译当前目录。更新 runtime、工具、infra、镜像 digest、命令、资源、连接或安全策略只能生成新版本并使受影响组合的预拉取证明失效。

只有通过 manifest、不可变 digest、供应链安全、基础自检和 WorkloadSpec 门禁的 runtime/组件才允许进入可编排目录；真实 runtime 动作、依赖闭包和 Kubernetes 启动验证决定具体组合与动作是否开放。动作或组合验证未通过时只关闭受影响动作或组合并返回明确原因；只有安全/供应链门禁失败才保持 `supply_chain.deployable=false`。

## 7. 多用户隔离

每个环境使用唯一的 tenant/session/environment 命名空间、Service、PVC 和 NetworkPolicy。普通实验只允许当前租户账号共享。跨校竞赛使用 M8 的显式 `contest_access_grant` 授权主体，grant 绑定组织方租户、竞赛、队伍、队员所属租户/账号、沙箱、能力集合、来源引用、版本和有效期；M8 是跨租户访问网关，先校验 grant 再调用 M2 内部受控主体契约。M2 的普通学生 HTTP 路由不能因为竞赛 grant 而切换租户，也不能把跨租户账号 ID 写入 `shared_account_ids`。撤销或版本递增必须立即阻断新请求，并关闭已有终端会话。

共享工作区采用沙箱级 `workspace_revision` 乐观版本校验，写入必须携带读取时的 `expected_revision`；版本不一致返回冲突而不是静默覆盖。链上的 deploy/tx/reset 按沙箱串行化，query 可并发。普通实验成员权限变更由 M7 小组行锁串行，先尝试把活跃沙箱和仿真会话授权收回到 owner-only，再写入新集合；任一跨模块清空或授予失败都不提交成员事务，已成功收回的资源保持 owner-only，剩余资源由重试继续收敛，同时关闭已撤销账号的终端、进度连接和仿真流。竞赛成员权限由 M8 `contest_access_grant.grant_version` 校验，未同步或已撤销的授权不得继续提供学生入口。

## 8. 旧实现清理清单

重构完成后以下实现不得保留：

- `base/chain-tools` 作为 runtime 默认 workspace/adapter sidecar 的注入；
- 后端按 `eco` 生成 runtime env/selftest/adapter 的 `switch` 和 Foundry 特判组合器；
- 按 `eco_tags` 批量预拉取工具；
- 不带 `composition_digest` 的预拉取接口和 runtime image 单布尔预拉取状态；
- 运行时目录顺序生成 ID、硬编码 runtime 版本；
- M5/M7/M8 各自编译组合或启动时重新读取当前目录；
- 旧 runtime/image/tool 请求字段、默认工具和兼容路由。
