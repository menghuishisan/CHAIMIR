# Chaimir 镜像分层与能力目录

> 本文是 `images/` 目录的职责说明和能力准入基线。它解释每一层、每个镜像负责什么，以及为什么要区分基础链能力和平台原生动作能力。
> 本文不定义固定组合矩阵；一次实验或竞赛使用哪些镜像，仍由实验配置、题目配置和 M2 编排器按 manifest 能力图动态生成。
> 当前目录审查基线：76 个 manifest，56 个正式不可变 digest 条目。本文不把“静态审查通过”表述成“所有镜像已经完成下载、构建和 Kubernetes 运行验收”。

## 1. 先看结论

镜像不是“某个实验的整套环境”，而是一个可验证的能力插件。一个镜像只声明自己的来源、进程、端点、能力、依赖、资源和安全边界；组合由运行期 `WorkloadSpec` 表达。

当前已经统一的规则如下：

- `runtime`、`infra`、`tool`、`judger` 等目录是职责层，不是固定搭配关系。
- `manifest.yaml` 的 `capabilities.provides/requires` 和命名 `bindings` 是组合契约；不存在“某条链只能搭配某个工具”的中心矩阵。
- 同一个实验可以有多个 runtime 实例。跨链组件通过 `source_chain`、`destination_chain` 等实例绑定连接到具体节点，不能隐式取“第一个 runtime”。
- L1 runtime 不是不可用镜像。它只提供已经验证的 RPC、peer、REST 等基础能力；调用未声明的原生 `deploy`、`tx`、`query` 时，拒绝的是当前动作或组合，不是整个镜像目录准入。
- 镜像目录准入、组合准入、runtime 原生动作准入和安全供应链准入是四个独立判定。

当前不能写成“全部无问题”的部分：

- `infra/chainlink-node`、`middleware/harbor`、`observability/grafana` 仍因安全/供应链门禁阻断，不能部署；不能靠改状态字段绕过扫描。
- `runtime/evm-besu` 的 Maven Netty/Jackson 补丁包已登记 55 个官方 SHA256，并在 Dockerfile 中逐件校验；仍需随镜像构建后的 Trivy、SBOM、Cosign 和运行闭环完成最终发布证明。
- `infra/op-stack` 的运行契约需要 `evm-engine-api` 和 `ethereum-beacon-api`。当前目录没有相应 provider manifest，因此只能在编排器明确提供这些插件后组成完整 OP Stack 工作负载，不能假装由普通 JSON-RPC 节点替代。
- `runtime/fisco-bcos` 的运行期 `config.ini` 由 M2 生成和验证；没有该配置时拒绝当前组合，FISCO 官方问题允许暂缓最终 M2 闭环，不把它误写成所有镜像的统一排除规则。

## 2. 两个容易混淆的 L1/L2

### 2.1 区块链架构中的 L1 和 L2

这里的区块链 L1 是提供共识、账本、交易执行或基础 RPC 的底层链，例如 EVM、Cosmos、Fabric、Aptos、Sui、NEAR、Solana、Substrate 和教育链。L2 是建立在某个 L1 之上的扩展或应用执行层，例如 Optimism 风格 rollup；它需要 L1 execution RPC、L2 engine API、Beacon API、rollup 配置和 JWT 等不同依赖。

所以项目仍然需要 L1/L2 区分：

1. 编排依赖不同。L1 可以独立启动；L2 必须通过命名 binding 找到一个或多个上游能力。
2. 交互语义不同。L1 提供基础链状态；L2 还涉及批次提交、派生、证明、排序或跨层消息。
3. 故障边界不同。L1 节点不可用通常影响其所有消费者；L2 还要区分 L1、sequencer、engine 和 beacon 端点的故障。
4. 题目和实验可以明确选择单链、双链或多链；平台不把某个链硬编码成唯一主链。

### 2.2 `runtime.adapter_level` 的 L1/L2/L3

manifest 中的 `runtime.adapter_level` 是“平台动作适配成熟度”，不是区块链协议分层：

| 适配等级 | 已承诺的能力 | 可以做什么 | 不能做什么 |
| --- | --- | --- | --- |
| L1 | 节点真实启动，并提供 manifest 声明的 RPC、peer 或 REST 基础端点 | 作为实验/竞赛中的基础能力 provider，被索引器、监听器、浏览器、工具和其他 runtime 通过 binding 使用 | 不能被平台原生动作接口调用未声明的 `deploy`、`tx`、`query` |
| L2 | L1 基础能力 + 镜像内真实 `deploy`、`tx`、`query` helper 和闭环自检 | 可以进入平台原生链动作流程，执行部署、交易、查询和声明的 reset | 不能凭版本探活或外部万能 helper 冒充闭环 |
| L3 | L2 闭环 + 该生态额外声明的高级能力，例如证明、重放、跨层或特殊状态恢复 | 只有自身 manifest、helper、自检和真实下游证据都闭合后，才能开放相应高级动作 | 不能只修改数字或在后端增加生态 `switch` |

因此，L1 不是“不能用”，L2 也不是“更高级所以所有链都必须强行做到”。没有原生合约部署语义的链，应保持 L1，直到换成具有相应模块的运行时并完成真实闭环。

## 4. 一个多镜像实验如何工作

例如一个“两个 EVM 节点 + 事件监听 + 浏览器 + 跨链中继”的实验，编排器会：

1. 创建两个不同实例编码的 runtime，例如 `source-evm` 和 `destination-evm`。
2. 为监听器建立 `chain` binding，指向 `source-evm` 的 `evm-json-rpc`。
3. 为中继器建立 `source_chain` 和 `destination_chain` 两个 binding，分别指向两个实例；中继器不能读取“第一个 runtime”。
4. 为浏览器建立自己的 RPC binding 和数据卷/数据库依赖。
5. 按所有组件的资源、安全、Secret、NetworkPolicy 和端口约束生成一个 WorkloadSpec。
6. 如果题目调用 runtime 的原生 `deploy/tx/query`，只检查被调用 runtime 是否达到 L2/L3；如果题目只需要 RPC、事件或浏览能力，L1 runtime 可以正常参与。

因此，在一个镜像里操作，其他镜像是否有反应取决于 binding 和协议：监听器订阅同一条链会看到事件，索引器会读取区块并更新数据库，中继器会在两条链之间执行自己的状态机；没有声明连接的镜像之间默认互不通信。

## 5. 新增镜像的插件化准入

新增链、工具或基础设施时，只需要提供新的目录和 manifest，但必须完成以下契约：

- 明确 category、进程、端口、卷、Secret、资源、安全和学生访问边界。
- 在 `capabilities` 中声明真实 `provides/requires/conflicts`，依赖组件使用命名 `bindings`。
- runtime 至少完成基础节点和 manifest 声明端点的自检；若声明 L2/L3 原生动作，必须提供镜像内 helper 和真实 deploy/tx/query/reset 闭环。
- 所有外部镜像、源码、构建基座和组件使用不可变 digest；源码下载或补丁包必须有可验证的 commit/摘要。
- 通过 Trivy、SBOM、Cosign、镜像拉取、容器自检和 Kubernetes WorkloadSpec 验证后，才进入对应准入状态。
- 不修改平台后端的生态 `switch`，不新增固定组合白名单，不恢复已删除的旧字段。

“加 manifest 即接入”表示平台不需要为每个新插件修改中心化组合代码；它不表示可以跳过镜像自身的真实性、安全性和能力自检。

## 6. 当前审查状态的准确表述

本轮已完成的是镜像层结构、manifest 结构、L1 基础能力语义、命名 binding、digest lock 引用和静态脚本/源码检查。尚未完成的是用户明确要求暂缓的全量下载/重建，以及依赖真实运行镜像才能证明的 Docker/Kubernetes 全闭环。

所以当前正确结论是：**镜像分层和插件化规则已经有统一解释，L1 可以作为基础能力使用；但不能宣称所有镜像已经最终准入。** 最终准入仍必须处理三个安全阻断、提供 OP Stack 缺失 provider，并按不可变 digest 完成构建、拉取、扫描、签名和运行验证之后再确认。
