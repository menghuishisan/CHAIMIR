# 镜像与容器设计

> 本文面向平台与镜像/基础设施工程师。平台是容器密集型(K8s)。本文定义全量镜像治理清单、构建规范、上游固定、仓库与分发、逐镜像职责与插件化收敛契约,是镜像设计的唯一真相源(SSOT);镜像是 M2 沙箱、M3 判题、M4 扩展仿真执行、M8 对局落地的基础。
> 最后更新:2026-08-26

## 一、镜像分类总览

| 类别 | 用途 | 数据驱动 | 大致数量 |
| --- | --- | --- | --- |
| `service` 平台服务镜像 | 后端单体、前端、迁移工具、受控定时任务 | 否 | ~4 |
| `runtime` 链运行时镜像 | M2 各区块链实例(EVM/联盟链/其他公链/自研),一个环境可有多个实例 | 是(runtime 表) | 首批 ~8,可扩展 |
| `infra` 区块链配套设施镜像 | 预言机/去中心化存储/索引/跨链/L2/账户抽象等链下生态 | 是能力组件 | 首批 ~10,可扩展 |
| `tool` 工具镜像 | M2 可接入工具(编辑/浏览/安全分析/通用) | 是(tool 表) | 首批 ~10,可扩展 |
| `judger` 判题执行器镜像 | M3 需容器化运行的判题套件/扫描器 | 是(judger 表) | ~5 |
| `sim` 仿真隔离执行镜像 | M4 扩展包通用运行器 + 重计算算法 | 是(sim_package) | 少量 |
| `sidecar` Sidecar 镜像 | 数据采集/日志 | 否 | ~2 |
| `init` Init 镜像 | 沙箱初始化/种子注入 | 否 | ~1 |
| `base` 基础镜像 | 上述镜像的构建基座 | 否 | ~5 |
| `middleware` 平台中间件镜像 | PostgreSQL、Redis、S3 对象存储、NATS、ClamAV、CouchDB | 否 | ~6 |
| `observability` 可观测镜像 | Prometheus、Grafana | 否 | ~2 |
| `ingress` 入口网关镜像 | ingress-nginx | 否 | ~1 |
| `network` 集群网络镜像 | CNI、策略执行与网络数据面 | 否 | 按集群能力 |

> 镜像层按镜像职责划分,不按后端模块划分;M2/M3/M4/M8 是消费者,不是目录边界。`images/` 本地目录名、镜像名前缀、Harbor Project、`manifest.yaml` 的 `category` 必须完全一致,统一取值为 `service`、`runtime`、`infra`、`tool`、`judger`、`sim`、`sidecar`、`init`、`base`、`middleware`、`observability`、`ingress`、`network`;禁止分类映射层、兼容别名和多套命名。
> `images/` 是**全量 Chaimir 运行期镜像治理目录**,不是只放平台自建 Dockerfile 的目录。平台自建镜像、官方薄封装镜像、纯上游固定镜像都必须在此登记 manifest、README、来源、版本、不可变 digest 锁定、许可、安全、端口、卷、备份、离线导入和学生权限。纯上游固定镜像的上游 digest 写入 manifest;平台自建、官方薄封装和构建基座镜像的生产 digest 统一来自 CI 推送后生成的 `image-digests.lock`,不得在 manifest 中维护第二套构建产物 digest 来源。配置和密钥变量名必须引用 `deploy/config/chaimir.env`;真实密钥值只由 Secret/KMS 在运行期注入同名环境变量,不得写入仓库、manifest、Dockerfile 或镜像层。
> 链运行时/配套设施/工具/判题器/仿真 均**数据驱动 + 插件化**:新增 = 加镜像 + manifest 入库,平台代码不改(呼应插件化架构)。M3 中由后端策略直接、安全承接的轻量判题能力不再重复做镜像,避免同一判题逻辑在后端和容器内双轨实现。
> **避免冗余**:同生态多变体按"教学目的"区分(开发体验/真实节点/轻量),不重复打包相同能力;通用构建输入可由 `base/chain-tools` 和 `base/fabric-tools` 复用,但 base 镜像只能参与构建,不得在运行期作为 runtime、tool 或学生入口 sidecar 注入。
> **沙箱身份契约**:`runtime`、`tool`、`judger` 以及由 M2 编排进沙箱 Pod 的 `infra` 镜像必须固定以 `1000:1000` 运行。薄封装镜像应复用上游已有 UID/GID 1000,不存在时在构建期创建;只允许对 `/workspace`、`/runtime-state`、工具声明的临时缓存目录、判题工作目录等必要路径做最小 `chown 1000:1000`,禁止 `chmod 777`、禁止 `chown -R /`、禁止保留 root group。M2 编排层保持 `runAsUser=1000`、`runAsGroup=1000`、`fsGroup=1000`,不得按镜像做 UID 兼容分支。

### 供应链引导根

Harbor 是为 Chaimir 镜像提供构建、签名、分发和准入的**外部供应链控制面**,不是实验、竞赛或 M2 WorkloadSpec 可编排的镜像能力。因此 Harbor 本体不登记为 `images/middleware/harbor`,也不进入依赖 Harbor 才能生成的 `images/image-digests.lock` 或 `PLATFORM_IMAGE_ATTESTATIONS_JSON`。保留它会形成“先由 Harbor 签名/分发 Harbor,才能启动 Harbor”的自举循环。

Harbor 的 chart、源码提交、组件闭包、补丁和离线 OCI 引导包改由 `deploy/charts/harbor/` 治理。该闭包仍必须逐组件完成源码重建、按 digest 拉取、Trivy HIGH/CRITICAL 阻断、SBOM、Cosign 签名和验签；首次安装前由经验证的 OCI 引导包预置到所有目标节点，chart 只引用其中的不可变 digest。Harbor 成功运行后，平台运行期镜像才进入普通 Harbor→候选锁→准入证明链路。Harbor 永远不可作为学生可选镜像、运行时能力或镜像组合成员。

## 二、镜像单元与运行期工作负载

镜像层和运行期编排必须分成两层,不得混用:

- **镜像单元(Image Unit)**:`images/<category>/<name>/manifest.yaml` 只描述一个可拉取镜像自身的来源、digest、许可证、端口、安全、资源建议、自检和离线分发。`upstream.components` 只表示构建来源或上游组件清单,例如判题镜像同时复用 Foundry 与 Node 工具链;它不是 Kubernetes 多容器编排定义。
- **运行期工作负载(WorkloadSpec)**:描述一次沙箱、判题或后端计算运行需要启动哪些组件、服务、路由、卷域和 NetworkPolicy。`runtime.adapter_spec`、`tool.resource_spec`、`judger.resource_spec` 复用同一套字段语义,但由各自模块按边界消费;M4 标准 `stdio-json` 能力的工作负载只由部署侧 `SIM_BACKEND_STDIO_ADAPTERS_JSON` 目录生成,不接受仿真包提交工作负载字段。
- **单组件也是 WorkloadSpec**:code-server、Remix、Jupyter、CLI 判题器等单进程场景也按单组件工作负载表达,不得保留一套单镜像字段和一套多组件字段并行。
- **组合不进镜像层**:Blockscout、Fabric Explorer、The Graph、Chainlink、IPFS Cluster、noVNC 等需要多进程或配套服务时,由运行期工作负载声明组件和路由;不得把 frontend/backend/proxy/db 强行塞进一个大镜像,也不得为某个工具写后端特判。
- **资源与网络按组件汇总**:配额校验、ResourceQuota、NetworkPolicy、Service、DNS、路由前缀和学生入口必须按运行期组件汇总生成。组合超出命名空间或租户配额时必须拒绝创建,不得静默降配或改端口。
- **边界不变**:M2 负责沙箱类 WorkloadSpec 编排;M3 通过 `internal/contracts.SandboxService` 申请 judge 沙箱或复用已有沙箱,不直接编排 K8s;M4 `compute=backend` 通过自有 `BackendAdapter` 或受控仿真运行器执行,不得直接调用 M2。

## 三、最终组合契约（唯一实现口径）

镜像是提供原子能力的可部署单元,不是预先绑定好的实验包。实验、解题赛和对抗赛均使用同一份 `CompositionSpec` 编译契约;差异只来自访问配置和生命周期,不得为不同业务维护第二套组合器或第二套兼容字段。

`CompositionSpec` 至少包含以下声明:

- `runtimes`: 每个环境声明一个或多个链运行时实例,每个实例有唯一组件编码、镜像版本、参数和能力；不存在“主运行时替代其他链”的隐式规则。平台原生 `deploy`/`tx`/`query` 由各实例自己的动作能力独立决定;
- `infra`: 教师明确选择的链下设施,以及由依赖解析器自动展开的必需配套;
- `tools`: 教师明确选择且对当前访问配置开放的工具;
- `links`: 组件间的有向连接,每条连接必须声明 `source_component`、`source_endpoint`、`target_component`、`target_endpoint`、`protocol`、`required_at_start`、`access_scope` 和 `config_binding`;
- `access_profile`: `experiment`、`contest-solve`、`contest-battle`、`vulnerability-prevalidate` 或 `judge-private`;
- `resource_profile`、`network_profile` 和经校验的组件参数。

镜像 manifest 的兼容性只能由结构化能力声明决定: `provides`、`requires`、`conflicts`、`cardinality`、`placement`、`config_schema`、`student_access`。`eco_tags` 只用于筛选和展示,不能单独判定可组合性,也不能生成隐式工具。无满足条件的组件、连接、资源、端口、权限或安全策略时,编译必须拒绝并返回用户可理解的原因及 `trace_id`。

组件选择分为三类且边界固定:

1. 教师可选择:一个或多个 runtime 实例、明确选择的工具和明确选择的基础设施;
2. 平台自动展开:manifest 的 `requires` 指向的依赖,例如 `thegraph-node` 的索引库,必须显示在组合预览中并随发布快照锁定;
3. 平台或系统专用:`external-secrets`、判题器、对抗赛官方匹配环境和受控预验证环境,不出现在学生或教师的普通工具选择器中。

高级视图是已编译组合的只读部署详情和连接图,用于审阅容器、资源、端口、NetworkPolicy、Service/DNS、挂载和审计信息。教师只能回到声明式编辑控件修改组件参数、组件选择或连接;不能编辑原始 `WorkloadSpec`、镜像地址/digest、启动命令、端口、安全上下文、NetworkPolicy 或 Secret。修改后必须重新编译、重新校验并生成新的草稿版本;已发布版本不可编辑。

编译生命周期只有一条路径: `draft` 声明 -> `validate` 能力/依赖/连接/资源/安全校验 -> `publish` 锁定镜像 digest 与完整快照 -> `start` 按快照生成 WorkloadSpec -> `recycle` 按环境生命周期范围回收。预拉取只针对已发布组合快照的镜像闭包,不得按运行时默认工具或全部生态标签工具预拉取。

一个环境可以有多个链运行时实例。所有跨组件访问必须通过能力解析和命名 `bindings`/`links` 连接到具体实例；不能由镜像名称、生态标签或“第一个 runtime”隐式绑定。L1 runtime 的基础 RPC/peer/REST 能力仍可参与组合，只有实际调用未声明的原生链动作时才拒绝。任何未声明的容器互访、端口映射、外网访问、Secret 共享、工具代理或跨租户连接均默认拒绝。不存在固定 N×M 兼容矩阵、默认工具隐式注入、旧字段双写、旧路由兼容或发布后原地修改。

`links.config_binding` 不是展示字段。编译器必须把它编译为目标组件可消费的受控环境变量或只读配置文件,值只能来自已解析的 Service DNS、声明端口和平台 Secret 引用;同时按连接生成最小 NetworkPolicy。启动前置连接必须等待目标健康后再放行源组件。无法生成绑定、目标端点不存在、协议不匹配或需要把私密连接信息暴露给学生入口时必须拒绝发布,不得保留只校验字段但不生成配置的半实现。

当前正式绑定语法为 `env:变量名`,方向为“源组件消费目标组件”。例如 Blockscout 连接 EVM 运行时时,组合必须声明 `source_component=blockscout`、`source_endpoint=web`、`target_component=chain-a`、`target_endpoint=rpc`、`protocol=HTTP`、`config_binding=env:ETHEREUM_JSONRPC_HTTP_URL`;追踪地址需另声明同目标端点的 `env:ETHEREUM_JSONRPC_TRACE_URL` 连接。编译器会把同一 Service 地址写入 Blockscout 的冻结工作负载,并生成对应的最小网络放行规则。没有这类连接的工具不会获得隐式运行时地址。

当目标协议为 `TCP` 或 `GRPC` 时,绑定值是 `ServiceDNS:端口`;当目标协议为 `HTTP`、`HTTPS`、`WS` 或 `WSS` 时,绑定值是带协议的内网 URL。Fabric 工具连接 peer 时必须显式声明 `env:CORE_PEER_ADDRESS` 并指向组合中选定 runtime 实例的 `peer` 端点,不能把运行时地址写死在工具 manifest 中。
Fabric Explorer 读取区块或提交链码还必须另声明 `env:CHAIMIR_FABRIC_ORDERER_ADDRESS` 到同一 runtime 实例的 `orderer` 端点;工具组件同时显式只读挂载 `runtime-state`,由运行时初始化的组织身份完成 peer CLI 认证。未声明任一连接或挂载时,组合编译必须拒绝调度。

## 五、链运行时镜像(M2,数据驱动)

每种链一个镜像模板,**预装节点 + 工具链 + 固化创世状态**(秒进优化)。每镜像携带 `manifest.yaml`(启动进程/端口/资源/健康检查/能力声明/适配器层级/自检套件)。manifest 不再隐式指定教师组合或默认工具;任何建议组合都必须转成草稿中的显式组件并在发布时锁定。下表为**完整接入图谱**(按生态分组,本文列出的镜像均需在 `images/` 层按生产标准逐个实现;后续新增生态仍通过数据驱动扩展):

> **实现目标(2026-08-23)**:目录登记、digest/供应链门禁和统一 `CompositionSpec` 编译只是接入基础,本文列出的 14 个 runtime、13 个 tool 和 4 个 judger 都必须补齐自身 manifest 声明的真实执行契约并通过各自的业务自检后可用。adapter_level:1 runtime 只需完成节点及其 RPC/peer/REST 等基础能力即可作为组合提供者;只有声明平台原生动作的 runtime 才必须额外通过 deploy/tx/query/reset 闭环。镜像拉取成功、Pod Ready 或静态版本命令成功不能替代已声明的核心能力或真实下游评测。供应链存在阻断的镜像必须通过安全版本、可验证源码重建或完成同等契约的替代实现消除阻断,不得绕过安全门禁直接翻转状态。

### 多容器编排(关键:一个沙箱 ≠ 一个镜像)

> **重要澄清**:一个沙箱实例往往是**一组协同容器(Pod 组)**,不是单镜像。M2 架构定义"每沙箱 = Namespace + Pod(s)"。运行时 manifest 声明该沙箱由哪些容器组成,控制面据此编排出多容器 Pod 组。

典型多容器编排:
| 实验场景 | 沙箱内的容器组 |
| --- | --- |
| Fabric 联盟链 | peer + orderer + CA + (可选)CouchDB 状态库 + (可选)fabric-explorer |
| EVM 攻防实验 | 链节点(geth/anvil) + 工具容器(Remix/blockscout) + 题目固化资产/教师脚本部署的依赖合约 |
| 多人联盟链组网 | 每个角色一个 peer 容器,组成一条链(多人共享,见 M7) |
| 混合实验 | 链节点容器 + collector sidecar(供 M4 取数) |

- **状态库**:Fabric 若用 CouchDB 富查询,CouchDB 作为该 Pod 的一个容器(或复用官方 couchdb 镜像),由 runtime manifest 声明;用内嵌 LevelDB 则无需。
- **工具容器**:web-embed 类工具(code-server/remix/blockscout)按独立受限 Pod 编排,只通过组合 `links` 获得声明的 Service 端点;需要读取运行时生成身份或公开配置的工具再通过 `mount_domains` 显式只读共享安全域,不得依赖同 Pod 或隐式互通。
- **运行时配置工具**:Fabric Explorer 等依赖链网络 profile、证书或配套数据库的工具,manifest 必须显式声明 `tool.runtime_config_required=true`;在运行时/实验 WorkloadSpec 没有真实生成这些配置前,seed 只能写入停用状态,不得因镜像已构建就标记可调度。
- 镜像层仍是"每种容器一个镜像",**编排(几个容器、怎么连)由 runtime manifest + M2 控制面负责**,镜像本身不耦合编排。
- **预拉取口径**:预拉取使用已发布 `CompositionSpec` 闭包中各镜像的 `prepull_command` 与 `prepull_hold`,命令必须来自镜像 `manifest.yaml` 的 `selftest.commands` 或同等受控声明。运行期 `command` 只表达容器真实启动方式,不得兼作镜像自检;多镜像组合必须用一个保持容器加若干 initContainer 覆盖快照闭包中的全部 runtime/infra/tool 镜像。
- **禁止固定组合矩阵**:`images/` 层不得维护 `composition.yaml`、固定 bundle、"某镜像只能搭配某镜像"等 N×M 关系。单镜像 `manifest.yaml` 只声明本镜像能力、生态标签、端口、安全域、资源和自检;具体容器组由 `runtime.adapter_spec`、实验/题目配置和 M2 编排器按数据动态生成。
- **组合校验位置**:M2 在 seed 与创建沙箱前按 manifest 的 `provides/requires/conflicts/cardinality/placement/config_schema` 校验能力依赖、同组 Pod 端口唯一、Service/DNS/路由名唯一、NetworkPolicy 放行范围、共享卷安全域和学生入口权限;`eco_tags` 只用于目录筛选和展示,不参与兼容判定。校验失败必须拒绝创建,不得在镜像层用固定白名单替代。沙箱创建时先建立运行时与工具的 ClusterIP Service,再按 `required_at_start` 顺序创建并等待 Pod;Service 先于 Pod 存在,避免消费者在目标组件就绪前解析不到声明地址。
- **工具安全域挂载**:工具组件如需使用运行时生成的身份或公开链配置,必须在组件 WorkloadSpec 中显式声明 `mount_domains`。M2 仅允许挂载当前组合已有的安全域,工具挂载一律只读;声明 `runtime-state` 时为该沙箱创建临时 PVC 并让运行时与工具共享同一卷,未声明不得以路径、环境变量或网络旁路读取运行态。学生入口组件禁止声明 `runtime-state`、`judge-private`。
- **受控执行目标**:`runtime.adapter_spec.workspace_ops.exec_target`、`private_archive_ops.exec_target` 和每个 `capability_commands.<action>.exec_target` 必须显式使用 `pod/container` 指向已声明容器。工作区执行目标必须是允许学生进入、挂载 `workspace` 且不能读取 `runtime-state`/`judge-private` 的容器;隐藏评测归档只能进入非学生入口;链能力执行目标必须是非学生入口并具备该生态原生 CLI/RPC 适配器。不能在线恢复创世态的生态统一使用 `capability_commands.reset_strategy=recreate_runtime`,由 M2 重建运行时计算 Pod 并保留工作区 PVC,禁止用固定成功值冒充 reset。控制面不得默认把 helper 命令执行到 runtime 实例容器,也不得假定所有生态都有同名通用链命令。
- **运行时原生 helper**:runtime manifest 的 `runtime.native.helper/profile/exec_target/reset_strategy` 与 `native.actions/methods` 是唯一能力装配字段。helper 可以显式位于运行时主容器,前提是镜像内确实同时包含对应原生 CLI/RPC 适配器且执行目标保持非学生入口;不得为了回避镜像构建把能力退回通用工作区容器。`native.actions` 只声明受控 argv,`native.methods` 只声明 RPC 方法,后端不得按生态解释;profile 必须落到真实可验证对象,deploy、tx、query 三个动作均须有下游状态证明。
- **镜像自检来源**:`runtime_container.prepull_command` 只验证 runtime 实例镜像本身;工作区 helper、基础设施和工具分别使用各自组件的 `prepull_command`。预拉取闭包不得用 `workspace_ops.selftest` 冒充 runtime 镜像自检。

### 端口与多人组网约束

镜像层只定义容器内部进程监听端口、协议、健康检查和用途,不定义宿主机端口。端口暴露、Service、Ingress、临时访问 URL、多人组网拓扑由 M2 沙箱控制面和部署层统一编排。

端口分层口径:
- **容器内部端口**:优先沿用官方默认端口,例如 PostgreSQL `5432`、Redis `6379`、geth/anvil RPC `8545`、Fabric peer `7051`。这样可以复用官方启动参数、SDK、健康检查和教学资料,不要为避免宿主机冲突而修改镜像内端口。
- **集群内部访问**:Pod/Namespace/Service 之间可以重复使用同一个容器端口,不会互相冲突;服务发现靠 Service/DNS 名称,不是靠宿主机端口区分。
- **本地宿主机访问**:只有开发者需要从宿主机直连数据库、Redis、S3 对象存储、链 RPC 等服务时,才允许在本地 compose/K8s 覆盖层做可配置端口映射,默认绑定 `127.0.0.1`,例如 `127.0.0.1:${CHAIMIR_DEV_POSTGRES_PORT:-15432}:5432`。
- **生产外部入口**:生产不暴露数据库、中间件和沙箱内部服务的宿主机端口;用户访问统一走平台网关、Ingress 或受控代理,并带鉴权、审计和租户/环境路由。

强制规则:
1. **禁止固定宿主机端口**:镜像、Dockerfile、manifest、启动脚本均不得写 `hostPort`、固定 `NodePort`、`hostNetwork: true` 或依赖宿主机端口范围;本地开发也只能通过 compose/K8s 覆盖层临时映射,不得进入镜像规范。
2. **容器端口只作契约**:`manifest.yaml` 只能声明 `containerPort`、协议、端口用途、是否需要平台代理暴露和健康检查路径;真实对外入口由控制面生成 Service/Ingress/Gateway 路由。
3. **同组 Pod 端口唯一**:同一 Pod 网络命名空间内,协同容器不得监听相同的 IP/端口组合;多人联盟链、工具 sidecar、collector 等组合由 runtime manifest 自检验证端口无冲突后才允许 seed。
4. **多人组网不共享宿主机端口**:多人实验按 `tenant_id`、`session_id`、`env_id` 生成 Namespace、Service、DNS 和 NetworkPolicy;角色节点通过集群内 DNS 互联,外部访问经平台网关带鉴权路由进入,不为每个用户分配宿主机端口。
5. **端口来自数据和配置**:业务服务端口、内部 RPC 端口、工具 Web 端口、健康检查端口均来自 `manifest.yaml` 或环境变量,禁止硬编码在后端代码、镜像入口脚本和部署模板中。
6. **冲突前置校验**:`seed-images` 与 M2 编排前必须校验 manifest 端口、Service 名、DNS 名、路由前缀和资源名唯一性;冲突直接拒绝接入,不得运行时静默改端口或做兼容映射。

因此,多人组网场景的端口冲突风险不通过"约定大家别占用同一宿主机端口"解决,而是通过不使用宿主机端口、按环境隔离命名空间和由控制面生成网络对象来消除。

### forked 运行时与特殊能力

- **forked 漏洞题**:由具 fork 能力的 EVM 运行时承担(`runtime/evm-foundry` 的 anvil fork 或 `runtime/evm-hardhat` fork 模式),无需独立镜像。出题阶段从真实链历史区块派生(经受控出网代理白名单,见 M2 安全),拉取所需状态后**固化进题目**;答题期锁定区块号 + 缓存状态,零外部依赖。

## 八、仿真隔离执行镜像(M4)

M4 的执行位置按**代码来源**分流(见 `docs/04-仿真可视化引擎/07-架构设计.md`):平台内置标准库
(41 个 `builtin__` 包)是随平台版本交付的 TypeScript,在浏览器 Worker 内运行,**无镜像**;
教师/第三方扩展包与少数重计算仿真在后端隔离容器内运行,对应本节两类镜像。

| 镜像 | 能力编号 | bundle 投递 | 承载 |
| --- | --- | --- | --- |
| `sim/package-runner` | `sim-package-runner` | 会话建立时经受控 k8s exec **stdin** 推入归档字节 | 全部教师/第三方扩展包 + 上架前的隔离预览 |
| `sim/<package-code>` | `<package-code>-stdio` | 无(算法固化在镜像内) | 同协议的重计算接入形态;**当前部署不登记任何一项**,`sim/graph-layout` 保留为该形态的接入示例(启用条件由本规范相关小节定义) |

### `sim/package-runner`(扩展包通用运行器)

它是**一个通用运行器,不是某个仿真的镜像**:镜像内只有平台自己的 Node ESM 装配器与 `stdio-json`
协议实现,不含任何仿真算法。新增一个教师扩展包**不新增镜像** —— 包正文由会话按需投递。
这与 `sim/<package-code>` 恰好相反,两者不可混用:前者承载不可信的外部代码且每会话内容不同,
后者承载平台已固化的算法。

- **bundle 走 exec stdin,不走网络**:计算 Pod 根文件系统只读且网络 deny-all,容器既写不下也取不到
  对象存储正文;放开网络就等于拆掉隔离边界。字节由后端从统一文件服务取出后直接推入容器标准输入,
  容器内先校验 sha256 与 `sim_package.bundle_hash` 逐字节一致再按 `meta.entry` 装配,
  **容器全程不持有任何凭据**。归档落在容器内唯一可写的 `emptyDir`,随命名空间删除一并消失。
- **只输出纯数据教学帧**:每次事件返回完整快照(`tick`/`state`/`view`/`current_step`/
  `interaction_availability`/`checkpoint_results`)与包自描述信息(操作清单、教学步骤、检查点、代码追踪)。
  扩展包的 `render` 也是外部代码,不能在浏览器执行,故渲染前的求值全在容器内完成,浏览器只画帧;
  而包内声明浏览器同样拿不到,只能由容器一并给出。
- **四条命令,容器不常驻状态**:`init`(装配后取初始状态)、`apply`(在已有事件后追加一条)、
  `restore`(只重放到给定事件位置,供回退、从头再来与断线重连恢复)、`verify`(上架前双跑比对 + 渲样例帧)。
  一次 exec 一个短命进程:状态由后端在命令里带回,容器崩溃、Pod 重建、后端换副本都不影响过程可复现。
- **输出是不可信输入**:后端在转发前按 TeachingFrame 协议校验(封闭模式数量与取值、`layout` 引用、
  规模上限),并按已入库的交互白名单核对包自描述信息里的 `emits` 与包身份,不合协议返回 `42011` 并终止会话。
- **同一镜像承担审核预览**:上架前的确定性双跑与样例帧渲制用同一个 runner 在同构隔离环境执行 ——
  "跑起来看效果对不对"本身就需要一个能安全执行第三方代码的地方,不为审核另建一套设施。

### `sim/<package-code>`(重计算算法镜像)

- `sim/<package-code>` 是单个重计算包的执行镜像,不是"覆盖所有仿真"的总计算包。仿真覆盖能力来自 M4 自描述仿真包协议、7 类平台可视化模式、审核与运行时;每新增一个重计算仿真,都必须新增 `sim_package` 版本、算法镜像与服务端受控能力目录项。
- M4 隔离执行适配器按**执行协议**复用,不得按算法复制 Kubernetes 生命周期代码。使用相同 `stdio-json` 协议的算法统一由共享 K8s 适配器执行;新增同协议算法只增加镜像、manifest、digest 证明和 `SIM_BACKEND_STDIO_ADAPTERS_JSON` 目录项,平台 Go 代码不改。只有出现长期驻留 gRPC、GPU 作业等不同执行协议时,才允许新增另一种适配器实现。
- 当前 `sim/graph-layout` 是该形态的接入示例,**不在默认能力目录内**:一条无法被任何 `sim_package` 引用的能力登记,只会让启动期 digest 证明校验为空转买单(判定与启用条件由本规范镜像准入门禁统一判定)。真正登记后,它由共享 `stdio-json` K8s 适配器消费:每个 WS 会话独立命名空间/Pod,每次事件通过受控 Kubernetes exec 把 JSON 写入镜像标准输入并读取标准输出。镜像只负责算法和算法输入校验,M4 负责鉴权、交互白名单、事件持久化、资源隔离、通用 I/O 上限、状态封装和回收。

### 两类镜像共用的隔离约束

独立命名空间(按会话)、deny-all NetworkPolicy(Ingress + Egress)、non-root、只读根文件系统、
禁止提权、丢弃全部 Linux capabilities、禁用 ServiceAccount Token、RuntimeDefault seccomp、
`pod-security.kubernetes.io/enforce=restricted`、requests/limits、就绪等待与单次执行超时;
断线、失败、归档均删除会话命名空间。镜像必须以完整 digest 命中 Cosign/Trivy 证明清单,
命令不经 shell,环境变量只来自部署配置且凭据语义键在启动时被拒绝。
一个会话一个 Pod,故受 `SIM_BACKEND_MAX_CONCURRENT_SESSIONS_PER_TENANT` 租户并发上限约束,
超限返回 `42005` 而不是继续建 Pod。

## 十二、构建规范

1. **来源类型决定 Dockerfile**:`source.type=platform-built`、`thin-wrapper`、`build-base` 必须有 Dockerfile,生产拉取 digest 只来自 CI 产出的 `image-digests.lock`;`source.type=upstream-pinned` 不重打包,不得有 Dockerfile,但必须有 manifest、README、上游不可变 digest、扫描、签名/准入和离线导入记录。
2. **non-root**:所有镜像以非 root 用户运行;M2 沙箱消费的 runtime/tool/judger/infra 镜像统一 `USER 1000:1000`,只读根文件系统(可写层限挂载卷)。
3. **多阶段精简**:构建与运行分离,最小化体积。
4. **可复现构建**:锁定基础镜像 digest 与依赖版本。Dockerfile 的镜像构建参数必须使用显式失败默认值,由 `images/build-images.ps1` 或共享 CI action 注入 Harbor digest;内部构建基座按依赖拓扑先构建,不得依赖目录字母顺序。
5. **统一分类**:`manifest.yaml.category` 必须等于本地目录名、镜像名前缀和 Harbor Project,只能取 `service`、`runtime`、`infra`、`tool`、`judger`、`sim`、`sidecar`、`init`、`base`、`middleware`、`observability`、`ingress`、`network`。
6. **manifest 驱动**:`manifest.yaml` 描述镜像元信息;`runtime`、`infra`、`tool`、`judger`、`sim` 由 `seed-images` 脚本写入对应业务表,实现数据驱动接入;`service`、`sidecar`、`init`、`base`、`middleware`、`observability`、`ingress`、`network` 用于构建/上游固定、签名、扫描、离线分发、准入策略和部署审计。
7. **统一供应链路径**:本地验收、预发布和生产都必须走同一条链路:构建镜像直接推送到 Harbor 分类 Project → 从 Harbor 解析不可变 digest 生成候选锁 → 按 digest 拉回 → Trivy/Cosign 门禁 → 通过后才生成正式 `image-digests.lock` 或准入证明。唯一职责入口为 `images/build-images.ps1`(构建与候选锁)、`images/pull-images.ps1`(按 digest 拉取)、`deploy/scripts/image-attestations-generate.ps1`/`deploy/ci/build-scan-sign-push`(扫描、SBOM、签名与验证)和 `images/sync-image-metadata.ps1`(晋升);不得再增加并行的本地刷新或发布编排。禁止用本地 Docker tag、`local` 镜像名、未推送镜像或手工 digest 作为验收依据。
8. **候选锁不等于准入**:`images/build-images.ps1 -DigestLockOut <candidate.lock>` 只能生成候选 digest 锁,用于回拉和安全校验。候选锁中任一镜像存在 HIGH/CRITICAL、SBOM 生成失败、签名或证明验证失败时,不得复制为正式 `images/image-digests.lock`,不得写入 `PLATFORM_IMAGE_ATTESTATIONS_JSON`,不得 seed 为可调度。
9. **代理不进入镜像来源**:公网慢或受限时,只能在 Docker Desktop、BuildKit、CI runner 或离线同步任务中配置代理/缓存/registry mirror;`Dockerfile`、`manifest.yaml`、`image-digests.lock` 和离线包清单必须仍记录官方 registry、官方上游 digest 或 Harbor 产物 digest。禁止把第三方镜像站、临时加速域名或个人代理地址写成镜像来源,避免本地和生产供应链分叉。
10. **产物元数据自动晋升**:后端流水线只产出 `service/backend`、`service/migrate`、`service/cron` digest,前端流水线只产出 `service/frontend` digest,通用镜像流水线不得重复构建这四项。每项 digest 只能在 Trivy 阻断扫描、SBOM 生成、Harbor 推送、Cosign 签名/证明和验证全部成功后写入统一片段。`image-metadata-promotion` 工作流串行合并片段,调用 `images/sync-image-metadata.ps1` 更新 `images/image-digests.lock`、`deploy/base` 与资源所属 component 的 Kustomize 镜像引用、受控仿真引用和环境静态准入列表;四个环境 overlay 不得复制 digest。同步器必须清除 catalog 已删除、已阻断或不再位于正式锁中的旧项,并拒绝任何可变 tag。`PLATFORM_IMAGE_ATTESTATIONS_JSON` 是全部可部署镜像的唯一环境准入证明;沙箱服务只校验本次编排引用的条目,不得把平台、网络或中间件镜像伪称为沙箱镜像。`backend/.env.example` 的准入列表保持空值,生产证明由 Secret/KMS 注入,不得把本地证明冒充生产配置。随后由机器人 PR 自动合并,禁止流水线直接写 `main`。机器人必须使用能触发 PR 检查的专用 `IMAGE_METADATA_BOT_TOKEN`,不得用默认 `GITHUB_TOKEN` 绕过或卡住检查链。
11. **禁止元数据回环构建**:`images/image-digests.lock` 与自动同步产生的部署引用只记录已完成的构建结果,同一逻辑镜像自己的 digest 晋升不得触发自身重建。共享基座 digest 变化是消费者的真实构建输入变化:backend 仅监听 `base/go-builder`、`base/runtime-min`、`middleware/postgres`,frontend 仅监听 `base/node-builder`,并各触发一次服务重建;随后服务 digest 晋升不得再次触发。镜像源码、Dockerfile、manifest、共享构建 action、应用源码或上述明确基座变化才触发对应产物流水线。晋升工作流缺少片段、签名/证明验证失败、引用无法映射或 PR 无法自动合并时必须显式失败,不得继续使用旧 digest。
12. **部署只认不可变引用**:平台服务 digest 只投影到 `deploy/base/kustomization.yaml`,按需资源 digest 只投影到其所属 component;四个环境 overlay 继承这些不可变引用且不得自行覆盖。staging 只在权威锁合入 `main` 后部署;生产发布从 tag 所指提交读取同一权威锁。两者都必须校验静态 overlay 渲染出的 `service/backend`、`service/frontend`、`service/migrate`、`service/cron` 与权威锁完全一致,任一缺失、可变或不一致就失败;不得再生成临时 digest overlay 或保留第二条覆盖路径。

## 十三、运行安全与生产门禁

镜像层按生产交付标准设计,不得出现只为演示可用的弱隔离、弱校验或临时降级路径。所有镜像在进入 Harbor 和 seed 前必须通过以下门禁:

1. **最小权限运行**:默认 `runAsNonRoot`、`allowPrivilegeEscalation=false`、只读根文件系统、显式 `drop` Linux capabilities;禁止 `privileged`、宿主机 PID/IPC/Network、宿主机路径挂载。确需例外的链节点能力必须写入 manifest 的安全例外字段,经安全评审后才能入库。
2. **网络默认拒绝**:沙箱 Namespace 默认 deny-all;只放行同一环境内被 manifest 声明的容器互通、平台控制面必要回调、对象存储/日志/指标等受控出口。fork 取链状态、下载依赖等出网行为只能走白名单代理,答题/判题期不得依赖公网。
3. **密钥不进镜像**:私钥、JWT、数据库密码、对象存储密钥、RPC 凭据、教师答案、flag、判题配置不得写入 Dockerfile、镜像层、构建参数和仓库;运行期只允许通过 K8s Secret、短期凭证或题目固化资产注入,并按权限最小化挂载。
4. **资源硬限制**:manifest 必须声明 CPU/内存/临时存储/PID/超时/并发限制和健康检查;判题与不可信代码镜像必须禁用默认出网并设置用后即毁策略。
5. **供应链可追溯**:平台构建镜像锁基础镜像 digest 并锁定依赖版本;纯上游固定镜像锁上游 digest 和许可证来源。所有可部署镜像都必须生成 CycloneDX SBOM,通过统一 Trivy 配置扫描并以 HIGH/CRITICAL 阻断,再由 Cosign 对镜像和 SBOM 证明分别签名、验证后才能部署。当前使用项目私钥且未部署私有 Rekor,本地、私有化和 CI 均关闭公共透明日志上传,不得向第三方端点发送私有仓镜像元数据;部署侧只按 digest 拉取。
   - 若上游最新正式版本仍触发高危门禁,镜像 manifest 必须在 `supply_chain.deployable=false` 写明 `block_reason`;供应链脚本不得把该镜像写入 `PLATFORM_IMAGE_ATTESTATIONS_JSON`,seed/调度也不得把它标记为可用。恢复只能来自官方安全版本、可验证源码重建或已完成契约适配的替代组件,不得跳过扫描、伪造证明或用本地例外绕过。
6. **启动显式失败**:入口脚本必须 `set -e` 等价处理错误,关键依赖、端口、权限、健康检查失败必须退出并暴露结构化日志;禁止吞错、自动降级到弱安全模式或写临时兼容分支。
7. **日志与数据脱敏**:日志不得输出密钥、token、私钥、flag、答案、学生代码全文和连接串;调试端口、管理后台、指标端点默认只在环境内可见,外部访问必须经平台鉴权代理。
8. **自检可复现**:每个镜像目录必须提供 selftest 或等价健康验证,覆盖启动、端口、权限、网络策略、资源限制和关键业务命令;未通过自检不得 seed 入库或标记可调度。

## 十四、学生可进入容器权限边界

学生能通过 Web 终端、IDE、调试工具或浏览器间接进入的容器,必须按"不可信用户环境"处理。学生容器只能看到完成实验所需的工作区、公开题面、公开链状态和经平台授权的工具,不能看到平台控制面、判题答案、其他用户或宿主机信息。

强制规则:
1. **学生入口与敏感容器分离**:学生终端默认进入 `tool` 或受控 `runtime` 容器;不得进入 `service`、`judger`、`init`、控制面 sidecar、数据库、中间件或含答案/flag/判题配置的容器。确需链节点交互时,只暴露受控 CLI/RPC,不开放高权限 shell。
2. **最小文件可见性**:学生容器只挂载本人/本队工作区和公开只读素材;不得挂载宿主机路径、Kubeconfig、ServiceAccount token、K8s Secret、平台配置目录、教师答案、判题脚本、隐藏测试用例、其他学生目录或控制面日志。
3. **关闭默认 ServiceAccount token**:学生可进入的 Pod 必须设置 `automountServiceAccountToken=false`;如确需访问平台 API,只能使用平台签发的短期、最小权限、按租户/环境绑定的令牌,并由网关注入/回收。
4. **共享卷分级**:同一环境内的共享卷分为 `workspace`、`public-assets`、`runtime-state`、`judge-private` 等安全域;学生容器只能读写被授权域。`workspace` 才是学生文件接口和代码持久化根目录;`runtime-state` 默认不对学生文件接口可见,只在显式快照策略下由 M2 受控保存;`judge-private`、flag、隐藏断言、评分脚本、教师私钥和答案永不挂载到学生容器。
5. **进程与系统信息收敛**:学生容器禁止 `privileged`、宿主机 PID/IPC/Network、Docker socket、container runtime socket、主机 `/proc`/`/sys` 敏感挂载和内核能力扩展;容器内只能看到本容器或本环境允许的进程与网络目标。
6. **网络只到必要目标**:学生容器默认不能访问数据库、Redis、S3 对象存储 管理端、NATS、Harbor、K8s API、元数据服务、控制面内部接口和其他环境 Namespace;只放行题目声明的链节点、工具、公开代理和平台授权 API。
7. **调试端点受控**:IDE、区块链浏览器、RPC、metrics、pprof、admin API 等端点不得裸露给学生;需要开放时必须经平台代理鉴权、按 `tenant_id/session_id/env_id` 路由,并记录审计。
8. **环境销毁清理**:学生环境结束后必须销毁 Pod、临时卷、短期凭证和路由;持久化产物只能通过平台文件/作业/报告接口按租户权限保存,不得遗留在节点本地目录。

## 十五、镜像仓库与安全

- **Harbor 私有仓库**,按统一分类分 Project:`service`、`runtime`、`infra`、`tool`、`judger`、`sim`、`sidecar`、`init`、`base`、`middleware`、`observability`、`ingress`、`network`。
- **安全门禁**:Trivy 漏洞扫描(高危阻断) + Cosign 签名(未签名不得部署)。
- **无本地分叉**:所有镜像引用必须使用 Harbor 分类命名空间和不可变 digest。本机 Docker 只允许作为构建缓存和调试执行环境;本地 tag 不能作为后端完整测试、K8s 预拉取、seed 或准入证明的来源。
- **预拉取**:官方/审核通过镜像经 M2 创建的 DaemonSet 在目标沙箱节点全节点预拉取(M2 秒进优化第一关)。预拉取粒度是已发布 `CompositionSpec` 的不可变镜像闭包,包含 runtime 实例、显式基础设施、依赖自动展开的基础设施、显式工具和该快照需要的 init/sidecar;不得按运行时默认工作负载或生态标签批量加入镜像。只有 DaemonSet 全目标节点 Ready 且无拉取失败事件时,才允许标记本次组合快照可预拉取。组合引用、自检命令、常驻用途、临时目录、可用状态或能力约束发生变化时,受影响快照的旧预拉取结果必须立即失效。每次执行使用唯一尝试标识条件写回,旧尝试不得覆盖中途失效或后发尝试。重新完成目标组合快照的全节点预拉取前不得进入教师编排目录或创建新沙箱。
- **自定义镜像审核**:教师/第三方上传镜像须经平台管理员审核 + 扫描后入预拉取池。

### 项目级 Docker 清理边界

- 可自动判定为 Chaimir 的 Docker 对象仅包括:`com.docker.compose.project=chaimir-supply-chain` 标记的供应链容器、`images/` catalog/正式锁/当前候选锁能映射的镜像引用,以及脚本明确创建的 Chaimir 临时标签。不得按创建时间、镜像体积或笼统名称猜测归属,不得执行全局 `docker system/image/volume prune`。
- 常规清理只删除已停止的供应链临时容器、已失去任何 Chaimir catalog/正式锁/当前候选锁引用且未被容器使用的临时标签和悬空层。运行中的容器、仍被任一不可变引用使用的层不得删除。Docker 删除最后一个 tag 时可能同时移除本地 RepoDigest;清理前必须逐项证明正式锁的全部 digest 在删除后仍可由 `docker image inspect image@digest` 访问,不能仅凭“同一 image ID”推断引用会保留。
- `images/build-images.ps1` 在成功推送后必定调用 `images/cleanup-local-images.ps1 -Apply`,清理旧的 `e2e-*`、`candidate-*`、`refresh-*`、`local-*`、`refactor-*`、`prepull-*` 临时标签和无正式/候选引用的悬空层;清理器删除前后均逐项校验不可变 digest,不下载恢复、不提供绕过清理的分支。
- Harbor Kubernetes 工作负载及 PVC、`chaimir-supply-chain-trivy-cache`、Docker registry 认证、Cosign 密钥和尚未完成晋升的证据均是可复用状态,不属于“冗余”。只有用户明确要求重置供应链数据时才能单独删除,且仍不得影响其他项目。

## 十六、私有化分发

- 私有化部署无法访问公网 Harbor:用**离线镜像包**(`docker save/load` 或 Harbor Replication)导入校内 Harbor。
- 镜像包按需裁剪(只含该校启用的链/工具/判题器/仿真包和必需中间件/可观测/入口组件),减小体积。
- 链运行时镜像、判题镜像、平台服务镜像和必需基础设施镜像随平台版本一起打包交付。
- 纯上游固定镜像作为 `upstream-pinned` 纳入离线包,按 `middleware`、`observability`、`ingress`、`network` 等统一分类导入对应 Harbor Project;不得因采用官方镜像而绕过 digest 锁、漏洞扫描、签名/准入、备份和网络策略。
- 离线包制作和校内 Harbor 预热统一使用 `images/pull-images.ps1`。脚本按 manifest 顺序逐个拉取 `image@digest`,默认读取已经由机器人 PR 晋升的 `images/image-digests.lock` 获取平台自建、薄封装和构建基座镜像 digest;缺少 digest 直接拒绝。单个镜像拉取失败后必须清理失败引用并重试,全部重试失败返回非 0,不得静默跳过或回退到可变 tag。完整功能测试也使用同一 Harbor + digest 锁:先用 `images/build-images.ps1` 将构建产物直接推入同一 Harbor 分类命名空间并生成候选锁,再用 `images/pull-images.ps1 -DigestLock <candidate.lock>` 按 digest 拉回并扫描。拉取脚本只消费不可变 digest,不得发布可变 tag,不得替代 Trivy/Cosign 门禁和正式 `image-digests.lock`。

## 十八、插件化收敛契约

镜像是一个不可变、可验证、可部署的原子能力单元，不是实验包、竞赛包，也不是固定组合矩阵中的一个格子。

| 类别 | 运行期角色 | 是否进入教师组合选择器 |
| --- | --- | --- |
| `runtime` | 提供一条具体链实例及其 RPC、peer、REST、账本和原生动作能力 | 是，可在一个环境中选择多个实例 |
| `infra` | 提供链下设施或协同服务 | 是，或由 `requires` 自动展开 |
| `tool` | 提供学生或教师使用的工具能力 | 是，必须显式选择 |
| `judger` | M3 私有判题能力 | 否，由平台/判题器专用流程选择 |
| `base` | 仅用于构建其他镜像 | 否，不能成为沙箱 sidecar 或学生入口 |
| `service`/`middleware`/`network` | 平台自身基础设施 | 否，不进入普通沙箱组合 |

镜像提供能力，`CompositionSpec` 决定组合。不能因为两个镜像都有相同 `eco_tags` 就认为它们可组合；也不能因为某个运行时存在就隐式注入工具。

镜像准入与组合可用性是两个独立判定：镜像通过 manifest、不可变 digest、供应链安全、自检和基础 WorkloadSpec 门禁后进入平台目录；组合编译再按该镜像的 `requires`、端点、参数、Secret 和 `links` 判断当前环境是否闭包。组合不满足条件时只拒绝当前组合并返回缺失能力或连接，不能把非安全问题写成 `supply_chain.deployable=false`，也不能因此把镜像从目录删除。

### 运行时插件契约

每个 runtime 插件必须在自身最终镜像内提供 manifest 声明的节点进程、端点和基础自检所需文件。需要平台原生链动作时，才额外声明 `runtime.native.helper`；该路径必须在最终镜像中存在，`exec_target` 必须指向一个已声明且非学生入口的容器。学生文件与终端能力由 M2 生成的 runtime 适配器统一声明为平台私有的 `tool/workspace` sidecar，并随每个实际 runtime 实例进入组合快照闭包；它不是教师可选工具，也不是 `base/chain-tools` 的运行时注入。若未来某个 runtime 需要不同的工作区实现，必须由该 runtime 适配器显式声明自己的私有 sidecar，不能在编排器中按生态或镜像名分支。

平台只依赖统一的 stdin/stdout JSON 协议：`deploy`、`tx`、`query` 和声明的 `reset`/`recreate_runtime`。`adapter_level: 2/3` 的 runtime manifest 必须为三个标准动作分别声明 `native.actions` 或 `native.methods`,并提供 `capability_selftest.deploy_payload` 与 `capability_selftest.query_target`;只声明版本探活且没有 manifest 声明的真实节点端点/基础自检的镜像才保持 `onboarding`,不能进入可编排目录。`adapter_level: 1` runtime 只要真实提供 manifest 声明的 RPC、peer 或 REST 基础能力,即可作为组合能力提供者进入目录,不开放未声明的原生动作。runtime manifest 的 `native.actions` 声明动作 argv,`native.methods` 声明 RPC 方法；平台只做边界校验和环境注入,不解释这些值。生态差异属于 runtime 插件自身；平台后端不得按 `eco` 维护适配器 `switch`,不得把一个中心化万能 helper 当作所有生态的实现。

`base/chain-tools` 可以继续作为构建基座或平台私有构建输入，但不得被注入为 `student-shell`、`chain-adapter` 或其他运行期组件。终端连接默认复用平台受控 exec/PTY；终端所依赖的文件操作 helper 可以由 runtime 的私有 workspace sidecar 提供，但必须在组合快照中作为实际镜像闭包登记，不能通过 base 镜像隐式提供。

运行时镜像的状态必须拆成三层，不能用一个字段混淆：

1. **镜像准入**：manifest、不可变 digest、供应链安全、基础自检和 WorkloadSpec 完整后，镜像进入平台目录。这个门禁对 `runtime`、`infra`、`tool`、`judger` 使用同一原则；只有明确安全/供应链阻断才禁止部署。
2. **组合准入**：组合编译器按 `provides/requires/conflicts/cardinality/placement`、端点、参数、Secret、连接和资源闭包判断一个镜像能否参与当前实验或竞赛。缺少依赖只拒绝当前组合，不能把镜像标成安全不可部署。
3. **运行时动作准入**：`adapter_level: 1` 只表示该 runtime 已能启动节点并提供 manifest 声明的基础能力（例如 RPC、peer、REST）；它可以作为环境中的节点/能力提供者参与组合，但不能被调用平台原生 `deploy`、`tx`、`query`。`adapter_level: 2/3` 只有在自身 helper、动作自检和真实下游闭环完成后，才开放这些动作。动作未闭合不影响该镜像作为其他组件依赖的节点或服务使用。

因此，L1 runtime 不是“不能进入实验/竞赛”，而是“作为基础能力提供者参与组合，但不能被调用未声明的原生链动作”。目录、前端选择器和组合编译器必须分别展示这三层状态，不能再把 L1 统一隐藏。

当前 runtime 目录的真实状态：`runtime/evm-foundry`、`runtime/edu-chain`、`runtime/evm-geth` 和 `runtime/evm-hardhat` 已声明各自镜像内的原生 `deploy`/`tx`/`query` helper 及能力自检。Foundry 已有正式 digest 的 Docker/Kubernetes 闭环；Edu、Geth、Hardhat 已完成当前候选 digest 的 Docker 闭环和 Kubernetes 多镜像闭环，但候选 digest 尚未完成 Trivy、SBOM、Cosign 证明，因此仍不得标记为最终可用或写入正式 digest 锁。`runtime/bitcoin` 已完成候选 digest 的 Docker 和 Kubernetes Service/DNS、真实 OP_RETURN、UTXO 交易、链查询闭环，进入候选 L2；它仍需完成正式供应链证明后才能进入可编排目录。`runtime/cosmos`、`runtime/evm-besu`、`runtime/fabric`、`runtime/fisco-bcos`、`runtime/move-aptos`、`runtime/move-sui`、`runtime/near`、`runtime/solana`、`runtime/substrate` 保持 `adapter_level: 1` 的基础组合能力：本轮已完成当前镜像的启动或基础 RPC/节点验证，但尚未提供平台原生动作闭环；它们仍可作为 RPC、peer、REST 等基础能力提供者参与组合。FISCO 的 `CHAIMIR_FISCO_CONFIG` 由 M2 生成并验证运行期 `config.ini`,缺少该配置时只拒绝当前组合,不阻断镜像目录准入。每个运行时完成自己的原生 helper、能力自检、镜像证明和真实下游闭环后，才单独提升动作等级。

#### 运行时准入修复门槛

只有要把某个 `adapter_level: 1` runtime 提升为“可调用平台原生链动作”时，才必须按该镜像自己的生态协议补齐原生 helper 和 manifest 能力声明，不能只修改等级或在平台后端增加生态分支。L1 的基础节点/RPC 能力仍必须先通过镜像和 WorkloadSpec 门禁，随后即可作为可组合能力提供者使用。提升动作等级至少要有以下可复现证据：

1. 镜像内 helper 真实完成 `deploy`、`tx`、`query`，以及声明的 reset 策略；不接受固定成功值、假交易哈希或仅版本探活。
2. Docker 冒烟通过后，在组合快照中完成运行时启动、依赖 Service/DNS 解析、核心动作和回收；工具通过显式 `links` 观察运行时状态时，必须验证源动作确实改变目标可见状态。
3. 重新构建并按不可变 digest 推送，完成 Trivy、SBOM、Cosign 签名与验证，生成候选锁；候选锁只有在正式证明通过后才能晋升到 `images/image-digests.lock` 和平台 attestation。
4. 只要任一动作或组合门槛未完成，只关闭受影响的动作或当前组合，并在自检详情中记录具体阻塞阶段；只有镜像安全/供应链门禁失败才标记为不可部署。不得用本地 tag、旧 digest 或手工 attestation 冒充准入。

#### 生产运行时接入即测

镜像没有本地/生产两套接入语义。所有验证都使用正式不可变 digest,在目标 Kubernetes 运行时执行：控制面通过 `POST /api/v1/sandbox/runtimes/{id}/selftest` 创建隔离沙箱,按 runtime manifest 的声明执行 `start/selftest -> deploy -> tx(若声明) -> query -> reset`,随后回收沙箱并持久化结果。该接口是运行时接入即测的唯一入口,不接受本地 tag、`latest`、宿主机源码挂载或旧缓存作为证据。

运行时自检通过只表示镜像内声明的进程和适配器在目标 Kubernetes 中完成了声明的闭环;仍必须通过镜像证明、完整镜像闭包预拉取、NetworkPolicy/资源限制、核心动作和回收验证,全部满足后才允许标记 `available`。

### Manifest 单一真相源

runtime、infra、tool、judger 的 manifest 必须使用同一套结构化能力模型：

`provides`、`requires`、`conflicts`、`cardinality`、`placement`、`config_schema`、`student_access`。

manifest 还必须完整声明最终 workload 所需的镜像 digest、版本、组件名称、启动命令、探针、自检命令、端口、环境变量名、Secret 引用、资源、安全上下文、临时目录和挂载安全域。seed 只做 schema 校验和规范化，不得丢弃这些字段后在后端按生态补写。

`infra` 与 `tool` 使用同一份能力和连接契约。`capabilities.requires/conflicts/cardinality/placement/config_schema/student_access` 必须原样进入 M2 的 WorkloadSpec，不能只保存 `provides`。需要其他组件端点的镜像必须声明结构化 `bindings`，每个绑定包含稳定角色名、所需能力、目标端点、协议、是否启动前置和 `config_binding`；绑定只能依赖能力和端点，不能写死 runtime code、镜像名或生态组合。组件能通过 TCP/HTTP 探活，不代表语义兼容；例如 EVM 事件监听、区块浏览器、ERC-4337 bundler/paymaster 只能要求 `evm-json-rpc`，不能用 `eco_tags` 或通用 `rpc` 端口替代。

多链组件必须使用多个命名绑定表达角色，而不是声明一个模糊的 RPC 环境变量。例如跨链中继可以声明 `source_chain` 和 `destination_chain` 两个绑定，二者都要求 `evm-json-rpc`，分别指向所选 runtime 实例的 `rpc` 端点；编译器根据能力、端点、冲突和组合参数解析提供者，并把两个 Service/DNS 地址分别注入源链和目标链配置。没有满足任一绑定时，只拒绝当前组合，不阻断该镜像的目录准入。

镜像 manifest 中的绑定使用以下固定结构；`bindings` 位于镜像类别节点（`infra`、`tool` 或 `judger`）下：

```yaml
bindings:
  - name: source_chain
    capability: evm-json-rpc
    endpoint: rpc
    protocol: HTTP
    required_at_start: true
    config_binding: env:HYP_SOURCE_RPC
```

`name` 是组件内稳定角色名，同一 manifest 不得重复；`capability` 和 `endpoint` 只引用提供者的结构化能力与端点；`protocol` 只允许 `TCP`、`HTTP`、`HTTPS`、`WS`、`WSS` 或 `GRPC`；`required_at_start` 决定启动等待与 NetworkPolicy 生效顺序；`config_binding` 当前只允许 `env:ENV_NAME`，其中 `ENV_NAME` 必须同时出现在该 manifest 的 `env_keys.config`，不得写固定 Service/DNS、镜像名或 runtime code。需要文件、Secret 或多个字段的协议配置必须由组件自己的入口读取平台生成的受控配置挂载，并在 manifest 中显式声明对应 mount/secret，不得把多个角色压缩成一个环境变量。

`postgres-compatible` 是数据库能力契约,不是固定镜像名。提供者必须声明 `postgres` TCP 端点并在组合参数中接受数据库名、用户和平台 Secret；消费者必须通过 TCP binding 获取 `ServiceDNS:5432` 形式地址,在自己的入口中生成官方 PostgreSQL URL,不得把原始地址直接当作 URL 或把 `middleware/postgres`、`infra/postgres-graph` 写死为依赖。消费者若需要密码,必须在 `env_keys.secret`/`secrets_required` 中声明同名 Secret,缺少凭据时入口拒绝启动。

组合声明必须支持多个 runtime 实例。runtime 实例使用组合内稳定的组件编码或实例别名区分，不能把第二条链塞进 infra/tool 或通过重复 `primary_runtime` 字段兼容。`workspace_runtime_instance` 必须显式指定承载工作区、初始化和学生文件入口的 runtime 实例；平台不得按数组顺序或字典序选择工作区运行时。跨链 relayer、跨链监听、双链判题等组件必须通过命名绑定连接多个 runtime；镜像只要通过自身安全/供应链门禁，就应进入镜像目录，由组合编译器在缺少所需链实例、端点或 Secret 时返回明确的组合错误。

组件需要密钥时只能声明 `secret_env` 引用，M2 在创建沙箱前把声明键从平台受控 Secret 同步到当前命名空间，再由 Kubernetes `SecretKeyRef` 注入；组合参数和连接地址仍分别来自声明参数与 `links`。`capabilities.config_schema.properties.<param>.x-chaimir-env` 是唯一的非敏感参数映射，值使用 `组件名/ENV_NAME`；单组件时也可以只写 `ENV_NAME`。编译器必须把 `CompositionComponentRef.params` 按该映射写入对应组件的字面量环境变量，并拒绝未声明映射、映射到 `secret_env` 或与 `links` 产生不同值的参数。禁止把密钥写入 `env.value`、镜像、组合 JSON 或宿主机文件，也禁止因为容器可以启动就省略必需 Secret 的就绪校验。

判题器额外在 `judger` 节声明 `runtime_code`、`genesis_ref`、非 shell `command`、受控 `exec_target`、字面量环境变量和 `suite_archive_name`；超时来自 `resources.timeout_seconds`。迁移层不得按判题器名称推断链、命令、脚本或安全策略。

生产镜像的最终地址和 digest 只能来自已验证的不可变证明清单；manifest 中的上游 digest、CI 生成的 `images/image-digests.lock` 和部署 attestation 必须经过同一校验器确认，不能形成三套互相漂移的真相源。

runtime 版本必须来自 manifest 的明确发布版本或 digest 派生版本，禁止使用全平台 hardcoded 日期字符串。runtime/tool/infra 的目录主键必须按稳定 code 生成或由数据库序列产生，禁止依赖目录枚举顺序。

### 唯一组合编译器

实验、解题赛、对抗赛、漏洞预验证和私有判题均调用 M2 的唯一 `CompositionSpec` 编译器。编译器执行：

1. 校验一个或多个 runtime 实例、显式 infra、显式 tool、参数和连接图。
2. 按 `requires` 展开依赖，检测循环、冲突、基数、placement、端口、安全域和访问配置。
3. 使用确定性的 provider 选择策略；存在多个同等 provider 时必须要求显式选择或返回歧义错误，不能取字典序第一个。
4. 将 `required_at_start` 编译为启动依赖和健康等待顺序。
5. 生成不可变 `composition_snapshot` 和 `composition_digest`。

同一组合中多个 runtime 若声明同名安全域，必须使用完全一致的挂载、访问、持久化和快照契约；否则只拒绝当前组合。共享工作区的容器路径始终来自显式 `workspace_runtime_instance`，不能从 runtime 数组顺序推断。

`eco_tags` 只能用于目录筛选和展示，不参与最终兼容判定。不存在固定 N×M 组合表、运行时默认工具、旧字段双写或业务模块自建组合器。

### 完整镜像闭包与预拉取

已发布快照的 `image_closure` 必须包含实际启动会用到的全部镜像：

- 每个 runtime 实例的镜像；
- runtime manifest 声明的 infra sidecar、init 和私有适配器镜像；
- 显式选择及依赖自动展开的 infra/tool 组件及其 init/sidecar 镜像；
- 每个镜像对应的不可变 digest、版本、预拉取命令、保持用途和临时挂载。

`ImageClosureItem` 同时冻结 `prepull_command`、`prepull_hold` 和 `ephemeral_mounts`;预拉取服务必须按快照逐项比对这些字段，不能只比较 URL 后重新解释当前目录。

预拉取状态必须按 `(runtime_image_id, composition_digest)` 唯一标识,由 `sandbox_composition_prepull` 保存状态、尝试 ID、DaemonSet、镜像列表、节点进度和失败原因；`runtime_image` 不承载组合级预拉取状态。

预拉取 API 必须显式接收已发布 `composition_digest`。预拉取、启动、恢复、工具挂载和回收只能引用该摘要对应的快照，禁止根据当前生态标签重新计算闭包。

### 发布和生命周期

M5 发布实验/题目时必须锁定每个环境的组合快照；M7/M8 起环境只能使用锁定快照，禁止在启动时重新编译当前目录。更新 runtime、工具、infra、镜像 digest、命令、资源、连接或安全策略只能生成新版本并使受影响组合的预拉取证明失效。

只有通过 manifest、不可变 digest、供应链安全、基础自检和 WorkloadSpec 门禁的 runtime/组件才允许进入可编排目录；真实 runtime 动作、依赖闭包和 Kubernetes 启动验证决定具体组合与动作是否开放。动作或组合验证未通过时只关闭受影响动作或组合并返回明确原因；只有安全/供应链门禁失败才保持 `supply_chain.deployable=false`。

### 多用户隔离

每个环境使用唯一的 tenant/session/environment 命名空间、Service、PVC 和 NetworkPolicy。普通实验只允许当前租户账号共享。跨校竞赛使用 M8 的显式 `contest_access_grant` 授权主体，grant 绑定组织方租户、竞赛、队伍、队员所属租户/账号、沙箱、能力集合、来源引用、版本和有效期；M8 是跨租户访问网关，先校验 grant 再调用 M2 内部受控主体契约。M2 的普通学生 HTTP 路由不能因为竞赛 grant 而切换租户，也不能把跨租户账号 ID 写入 `shared_account_ids`。撤销或版本递增必须立即阻断新请求，并关闭已有终端会话。

共享工作区采用沙箱级 `workspace_revision` 乐观版本校验，写入必须携带读取时的 `expected_revision`；版本不一致返回冲突而不是静默覆盖。链上的 deploy/tx/reset 按沙箱串行化，query 可并发。普通实验成员权限变更由 M7 小组行锁串行，先尝试把活跃沙箱和仿真会话授权收回到 owner-only，再写入新集合；任一跨模块清空或授予失败都不提交成员事务，已成功收回的资源保持 owner-only，剩余资源由重试继续收敛，同时关闭已撤销账号的终端、进度连接和仿真流。竞赛成员权限由 M8 `contest_access_grant.grant_version` 校验，未同步或已撤销的授权不得继续提供学生入口。

### 旧实现清理清单

重构完成后以下实现不得保留：

- `base/chain-tools` 作为 runtime 默认 workspace/adapter sidecar 的注入；
- 后端按 `eco` 生成 runtime env/selftest/adapter 的 `switch` 和 Foundry 特判组合器；
- 按 `eco_tags` 批量预拉取工具；
- 不带 `composition_digest` 的预拉取接口和 runtime image 单布尔预拉取状态；
- 运行时目录顺序生成 ID、硬编码 runtime 版本；
- M5/M7/M8 各自编译组合或启动时重新读取当前目录；
- 旧 runtime/image/tool 请求字段、默认工具和兼容路由。
