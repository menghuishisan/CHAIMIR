# Chaimir 前后端全面安全与规范复核报告

## 1. 结论摘要

本次复核不能得出“所有安全问题均已解决”的结论。源码层面的明显高危模式未发现，React Router advisory 1124282 已不在当前依赖锁文件中，前后端单一启动入口、镜像 digest、HTTP 限制、认证 Cookie、CSRF 自定义头、前端危险 DOM sink 等控制已具备证据；前端令牌曾存在文件级分散，现已统一；本次二次复核还发现并修复了刷新接口文档与实现不一致的问题；但仍有以下未闭环项：

1. 验收 seed 的自检状态问题已修复：seed 现在写入待自检/不可调度状态，必须经过正式 selftest 才能进入可用状态；真实集群仍需执行该流程验证。
2. WebSocket 同源判断的原问题已修复并有单元测试覆盖；真实 Ingress/旁路访问仍需运行时验证。
3. 固定版本 `gosec`/`govulncheck` 已在当前工作区实际运行通过；`govulncheck` 报告的依赖树漏洞不在本项目可达调用路径。
4. K8s RBAC、Ingress/TLS、Sigstore 拒绝路径、ClamAV 数据库新鲜度、完整镜像复扫及 race 测试仍需要真实环境验收。
5. 旧审计文档已补充历史快照标识；其中的旧 `:dev` 镜像和判题模型结论不再作为当前发布依据。
6. 刷新接口旧的 `refresh_token` 请求体描述已从 M1 接口文档和 OpenAPI 中删除，改为 Cookie + `X-Chaimir-Refresh: 1` 的唯一契约。

因此，本报告将“已验证控制”“代码问题”“运行时未验证门禁”和“历史文档漂移”分开，不把自动扫描无输出理解为安全闭环。另经核对,`acceptance_seed*.go` 的固定运行时/判题器数据只受 `ensureAcceptanceSeedAllowed` 的 `local/dev` 门禁保护,属于 `docs/总-工程目录设计.md:92` 明确允许的验收夹具例外;生产运行时、镜像和工具仍由 M2 管理接口登记,内置仿真包由 `SyncBuiltinPackages` 同步,没有把验收夹具误当生产初始化的证据。

## 3. 未闭环问题（按严重性）

### AUDIT-001 已修复：验收 seed 伪造判题器自检通过状态

原问题证据：`backend/cmd/migrate/acceptance_seed_rows.go` 原先对 `evm-foundry` runtime、`solidity-unit` 和 `onchain-assert` 直接写入通过状态，但 seed 函数没有调用正式 runtime/judger selftest 路径。

原影响：数据库状态会声称判题器已通过自检，但没有证明镜像、运行时、工具链、Genesis 或隐藏测试真实可执行。验收或调度逻辑若仅依赖该状态，可能使用未验证的判题配置。

修复：`backend/cmd/migrate/acceptance_seed_rows.go:82-84` 现在写入 runtime 待自检/接入中状态，`:116-144` 写入 judger 待自检/停用状态；正式 selftest 成功后才由 `RunRuntimeSelftest`/`RunJudgerSelftest` 更新为可调度。未完成 selftest 时，sandbox/judge 的已有可用性检查会拒绝调度，形成 fail-closed。

### AUDIT-002 已修复：WebSocket 代理协议头信任边界

原问题证据：`backend/internal/platform/ws/hub.go` 原实现直接读取 `X-Forwarded-Proto`，没有检查请求来源是否属于受信代理。

修复：`backend/internal/platform/ws/hub.go` 现在解析 `HTTP_TRUSTED_PROXIES` 网段，只允许来源地址命中可信网段时使用 `X-Forwarded-Proto`；`backend/cmd/server/main.go` 将同一配置传入 Origin 策略。新增 `backend/internal/platform/ws/hub_test.go` 覆盖可信代理和直连伪造两条路径。

剩余验证：需在真实 Ingress 和直连后端路径分别验证请求头覆盖、Service 暴露面和拒绝结果；这属于 AUDIT-006 的运行时门禁。

### AUDIT-003 已修复：前端无入口的 Vite 双轨配置

原问题证据：`frontend/apps/web/vite.config.ts` 曾硬编码 `port: 5173` 和 `host: true`；`frontend/package.json` 与 `frontend/apps/web/package.json` 已移除平台前端 `dev` 启动脚本，实际入口是 `deploy/Makefile:35-36` 的 `make dev-up` + Ingress HTTPS。

修复：已删除 `vite.config.ts` 中无入口的 `server` 配置，保留唯一平台启动入口，不引入环境变量驱动的第二条开发链路。

剩余验证：前端构建和统一部署入口已通过本轮检查。

### AUDIT-004 已修复：SAST 门禁可复现性

证据：按 `.github/workflows/backend.yml:89-96` 的固定版本命令实际执行：`gosec@v2.28.0` 扫描 284 个文件、70,886 行，`Nosec=0`、`Issues=0`；`govulncheck@v1.1.4` 报告本项目代码无可达漏洞，依赖包级漏洞为 0。此前发现的 `github.com/klauspost/compress` 与 `github.com/Azure/go-ntlmssp` 已分别升级到 `v1.18.7`、`v0.1.1`；剩余 1 项仅为 `golang.org/x/crypto` 模块中未被调用的 OpenPGP 模块告警，当前无修复版本且项目只使用 Argon2。

结论：本机门禁已可复现通过；仍需保持 CI 使用同一固定版本，不得用 `nosec`、注释或“扫描超时”代替修复。

### AUDIT-005 已修复：历史审计文档与当前实现漂移

证据：`docs/审计-后端路由安全暴露面-2026-06-28.md:113-117` 仍声称 `chaimir/frontend:dev`、`solidity-unit:dev` 及旧的 judger 执行模型；当前 `deploy/overlays/local-dev/kustomization.yaml` 使用 Harbor digest，当前判题通过 M2 sandbox 命令和私有 sidecar 执行。

原影响：维护者会根据已过时的结论重复修复或错误地绕过当前模型，违反文档与实现单一真相源要求。

修复：`docs/审计-后端路由安全暴露面-2026-06-28.md` 已明确标注为历史快照，并指向本报告；当前模型结论为 judger 镜像通过 `execution_sidecars` 进入沙箱，`executor_ref` 只是数据引用。仍然有效的 seed 自检问题已单独保留为 AUDIT-001。

### AUDIT-006 中：真实集群门禁尚未闭环

本轮未对真实集群执行以下攻击/拒绝路径：未签名镜像拒绝、RBAC `can-i`、Ingress/TLS 实际响应头、NetworkPolicy deny-all、ClamAV 数据库新鲜度、完整镜像复扫、沙箱创建-判题-回收和 race 测试。当前 kubeconfig 的 `docker-desktop` 上下文指向 `127.0.0.1:63761`,只读 `kubectl get nodes` 因服务未启动而无法连接；源码与 Kustomize 渲染通过不等于这些运行时属性已证明。

这不是把本地测试留给用户自行补做的代码缺陷:这些检查依赖真实 Kubernetes、Ingress、镜像仓库和节点状态,当前工作区没有可替代的运行时证据。除本节列出的真实环境门禁外,本轮未发现其他源码安全问题、前后端启动双轨或未受门禁保护的验收夹具路径。

## 4. 已验证控制

- 模块边界：未发现跨业务模块直接导入；各模块访问自己的 sqlc 生成代码，跨模块协作使用 contracts/平台能力。聚合层和审计/通知统一约定仍需以运行时集成验收补证。
- 后端 HTTP：`backend/cmd/server/main.go:67-75` 配置读写/空闲/请求头超时和 `MaxHeaderBytes`；`:197-204` 设置请求体上限；`httpx` 对请求体和 Redis 限流失败路径显式处理。
- 认证与网络：`backend/internal/platform/auth/middleware.go:65-89` 使用 HttpOnly、Secure、SameSite Cookie；`backend/internal/platform/netx/netx.go` 对公网 URL、私网/本地/元数据地址、DNS 解析和请求超时有边界控制。
- CSRF：`/auth/refresh` 依赖 Refresh Cookie 时要求 `X-Chaimir-Refresh: 1` 自定义头；sandbox Web 工具代理使用路径 Cookie 时，对 `POST/PUT/PATCH/DELETE` 统一执行 Fetch Metadata 优先、Origin/Referer 精确同源校验。两处均不把 SameSite 当作唯一防护。
- 前端危险面：未发现 `dangerouslySetInnerHTML`、`innerHTML`、`outerHTML`、`insertAdjacentHTML`、`document.write`、`eval`、`new Function`；扫描到的 `postMessage` 仅用于模拟 Worker 内部消息，不是跨窗口信任边界；没有原始 fetch/XHR 双轨，API 经集中 client；本地存储未发现保存访问令牌/密码，密码和待登录凭证只存在组件内存态。
- 前端安全头：`images/service/frontend/security-headers.conf:1-21` 定义 CSP、nosniff、Referrer-Policy、Permissions-Policy；`images/service/frontend/nginx.conf:37-53` 在健康检查、静态资源和应用入口均 include。实际镜像/Ingress 响应头仍属于 AUDIT-006。
- 依赖：`frontend/pnpm-lock.yaml` 为 React Router 8.3.0，未发现 advisory 1124282；`pnpm audit --prod` 返回无已知漏洞。
- 镜像与入口：local-dev overlay 的应用和中间件镜像使用 Harbor digest；平台浏览器入口统一为 `make dev-up`，没有恢复 standalone frontend 或 `local-deps` 第二条链路。
- 注释与抑制：backend/frontend/deploy（排除第三方 vendor/CSI 生成内容）未发现 `nosec`、`nolint`、TODO/FIXME 等以注释抑制问题的新增痕迹。

### AUDIT-007 已修复：前端令牌文件级双真相源

原问题证据：`frontend/packages/ui/src/tokens/theme.css` 的自定义工具类引用了布局、层级和动效运行令牌，但这些变量此前同时定义在 `base.css`，违反 `docs/总-前端设计规范.md` FE-1 的单一真相源要求。

修复：布局、层级和动效运行令牌现全部定义在 `frontend/packages/ui/src/tokens/theme.css`；`frontend/packages/ui/src/tokens/base.css` 只保留全局基础样式，不再声明同类令牌。前端 lint、类型检查和构建在统一后重新通过。

### AUDIT-008 已修复：Cookie 认证状态变更缺少应用层 CSRF 门禁

原问题证据：`backend/internal/modules/identity/api_auth.go` 的 `/auth/refresh` 使用 HttpOnly Refresh Cookie 执行会话轮转，sandbox Web 工具代理也允许路径受限 access Cookie 转发非安全方法；此前两处均没有应用层 CSRF 校验，只依赖 Cookie 的 SameSite 属性。`security-best-practices` 的 GO-HTTP-006/REACT-CSRF-001 明确要求 Cookie 认证的状态变更接口具备 CSRF 防护，SameSite 只能作为纵深防御。

修复：`backend/internal/platform/auth/middleware.go` 定义统一的 `X-Chaimir-Refresh: 1` 自定义头校验，刷新 handler 缺失或值不匹配时立即拒绝；`frontend/packages/api-client/src/client.ts` 的唯一刷新请求统一携带该头。对路径 Cookie，`BrowserAccessMiddleware` 只对非安全方法启用 Fetch Metadata 优先、Origin/Referer 精确同源校验，Bearer 和一次性 query token 不受影响。跨站表单不能设置刷新自定义头，Refresh Cookie 保持 `HttpOnly; Secure; SameSite=Strict`，工具 Cookie 的原有路径限制和 `SameSite=Lax` 仍保留以支持工具顶层进入。

### AUDIT-009 已修复：刷新接口文档保留已删除的 Refresh 请求体双轨

原问题证据：运行时代码 `backend/internal/modules/identity/api_auth.go:113-132` 只从 HttpOnly Cookie 读取 refresh token，并要求 `X-Chaimir-Refresh: 1`；但 `docs/01-身份与租户/03-接口设计.md` 原先仍描述请求体携带 `refresh_token`，认证流程文档仍写“Access + Refresh”，OpenAPI 也没有声明新的门禁头。

影响：实现、前端 SDK 和接口文档对同一认证流程形成两套契约，调用方可能把长期凭证重新放回请求体，造成凭证泄露和 CSRF 防护绕过；这属于规范与安全边界漂移，不是可以忽略的注释问题。

修复：M1 接口文档改为“空 JSON + `X-Chaimir-Refresh: 1` + HttpOnly Cookie”，登录响应明确只返回 access token；业务流程图改为 Cookie 轮转；`backend/api/paths/identity.yaml` 增加必填头及枚举值。全仓复搜不再存在旧请求体描述。

## 5. 规范与重复实现结论

已符合或有证据支持的部分：模块边界、集中 API client、统一 Ingress HTTPS、环境镜像 digest、错误显式返回、前端危险 sink 禁用、Lucide/令牌化设计方向。前端令牌文件级双真相源已在 AUDIT-007 修复。

验收 seed 与正式注册/自检流程是文档明确允许的 local/dev 验收夹具和生产管理流程两种生命周期，不是生产在线双轨；seed 受 `ensureAcceptanceSeedAllowed` 门禁保护，生产不会执行。历史文档已标记为快照，Vite `server` 配置也已删除。`frontend/packages/api-client/src/client.ts` 中刷新请求使用独立 `axios.post` 只是为避免响应拦截器递归，不是第二套 API client。当前没有证据表明存在未受门禁保护的第二套在线 API client、第二套前端启动入口、跨模块直接调用实现、同一令牌的重复定义或第二套 Cookie 刷新流程。
