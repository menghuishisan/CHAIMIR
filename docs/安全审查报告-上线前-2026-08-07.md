## High

### SEC-002（已修复）：私有化生产 Overlay 未配置 TLS，违反“全站 HTTPS”契约

状态：已修复并通过 `kubectl kustomize` 输出检查；仍需在真实 Ingress Controller 验收证书链和 301/308 行为。

- 证据（修复前基线）：该 Overlay 曾仅替换 Ingress host，没有 `spec.tls`；当前 Base Ingress 统一声明 `chaimir-tls` 和 HTTPS 重定向,各 overlay 只替换域名或证书签发方式。项目部署规范明确要求“全站 HTTPS”（[docs/总-部署架构设计.md](总-部署架构设计.md:165)）。
- 影响：校内网络的被动监听者或中间人可以窃取密码、Bearer JWT、Refresh Token 和登录响应，随后接管账户。
- 修复：Base 和 public-deny Ingress 统一声明强制 TLS、HTTPS 重定向与 `chaimir-tls`；各 overlay 同步替换规则域名和 TLS SNI 域名。prod-saas 使用 cert-manager 注解，staging 由集群预创建 Secret，prod-school 由交付运维提供 Secret，均不允许降级为 HTTP。
- 验收：渲染每个 overlay 后两条 Ingress 均必须含匹配规则域名的 `spec.tls`；TLS Secret 必须是 `kubernetes.io/tls` 且同时包含证书和私钥；HTTP 请求必须 301/308 到 HTTPS；浏览器中登录、刷新和工具代理均无 mixed content。

### SEC-003（已修复）：Access Token 和 Refresh Token 持久化在 JavaScript 可读取的 Web Storage

状态：已改为 HttpOnly refresh cookie + 内存 access token；以下证据描述的是修复前基线。

- 位置：[frontend/apps/web/src/utils/authSession.ts](../frontend/apps/web/src/utils/authSession.ts:17) 第 17-23、61-70、76-78 行。
- 证据（修复前基线）：登录与轮转后曾把两类令牌写入 `localStorage` 或 `sessionStorage`；当前只保留内存 access token 和 HttpOnly refresh cookie。
- 影响：任意同源 XSS、恶意浏览器扩展或被攻破的同源脚本可同时窃取短期 Access Token 和长期 Refresh Token；Refresh Token 可轮转并维持会话，单端登录和短 Access TTL 都不能有效阻断已窃取凭据。
- 修复：将 Refresh Token 改为服务端设置的 `HttpOnly; Secure; SameSite` Cookie，Access Token 仅保存在内存并通过同源刷新恢复；随之为 Cookie 认证状态变更请求加入 Origin/CSRF 防护。不要以 sessionStorage 作为安全替代。
- 验收：静态检查不得再出现 `access_token`/`refresh_token` 写入 Web Storage；浏览器开发者工具的 Storage 面板不得出现凭据；XSS 回归用例不能读取或刷新会话。

### SEC-004（已修复）：HTTP 服务缺少完整连接超时、MaxHeaderBytes 与全局请求体上限

状态：已增加 Read/Write/Idle timeout、MaxHeaderBytes、JSON/multipart `MaxBytesReader` 和配置校验。

- 位置：[backend/cmd/server/main.go](../backend/cmd/server/main.go:67) 第 67-71 行、[backend/internal/platform/httpx/httpx.go](../backend/internal/platform/httpx/httpx.go:35) 第 35-54 行。

- 影响：攻击者可以维持慢速请求、耗尽连接/worker，或发送极大 JSON body 占用内存和 CPU，造成控制面拒绝服务。
- 修复：在配置中引入并强制校验读、写、空闲超时与最大 Header；在路由中按业务类别包裹 `MaxBytesReader`，默认拒绝超限 JSON，只有明确的大文件路由拥有单独额度；Ingress 同步限制 body size。
- 验收：用慢速 body/header、超大 header、超限 JSON 的集成测试确认请求在限定时间/大小内被拒绝且 Pod 内存不持续增长。

### SEC-005（已修复）：multipart 上传在业务大小校验前可无界落盘/占用资源

### SEC-010：内部服务签名未绑定服务身份，且 APP_HMAC_KEY 为全局共享密钥

- 位置：[backend/internal/platform/auth/middleware.go](../backend/internal/platform/auth/middleware.go:496) 第 496-565 行、[backend/internal/platform/config/config.go](../backend/internal/platform/config/config.go:119) 第 119-127 行。
- 证据（修复前基线）：中间件曾要求服务头但未把服务名纳入签名；当前签名串已包含服务名。每调用方独立密钥和来源白名单仍是生产纵深防御增强项。
- 影响：任何取得该共享密钥的内部工作负载都可以把服务名改成其他值，并构造任意合法格式的 `source_ref`；如果目标内部接口只依赖服务签名而没有额外来源绑定，攻击者可扩大可调用的内部契约范围。当前公网 Ingress 对 `/internal` 有阻断，因此这是集群内横向移动和纵深防御风险，不等同于已证明的公网未授权。
- 修复：至少把 `service` 纳入签名；更稳妥的方案是每个调用方使用独立 Secret/密钥并在服务端按服务名选择验证密钥，同时对 `service -> source_ref 前缀 -> 路由` 建显式白名单。为重放保护增加一次性 nonce/短期缓存，而不是只校验时间窗口。
- 验收：使用 A 服务密钥伪造 B 服务名必须失败；合法服务只能访问其声明的内部路由和来源前缀；同一签名在窗口内重复提交必须被拒绝或具备幂等保护。
