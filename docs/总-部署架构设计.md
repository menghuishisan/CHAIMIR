# 部署架构设计

> 本文面向 SRE、部署与平台工程师。双形态部署:SaaS 公网统一运营 + 学校私有化。K8s/k3s 编排,Kustomize 分层,CI/CD 自动化。
> 最后更新:2026-08-23

---

## 一、双形态部署

| 形态 | 编排 | 租户 | 平台管理员 | 镜像分发 |
| --- | --- | --- | --- | --- |
| **SaaS 公网** | Kubernetes | 多租户(school_id + RLS) | 有 | 公网 Harbor + 上游 digest 锁 |
| **私有化(单校)** | k3s(轻量) | 单租户(tenant_id 恒定) | 无(学校管理员顶层) | 全量离线镜像包 |

- 同一套代码、同一套镜像;差异仅配置(deploy_mode、是否启用 platform 层)。前端镜像是唯一静态 SPA,
  不在构建期固化部署形态;每个 Kustomize overlay 生成 `chaimir-frontend-runtime-config` ConfigMap,
  以只读 `/runtime-config.js` 挂载并在应用模块加载前注入 `deploymentMode` 与独立工具 origin。
  该运行时配置是前端装配层唯一来源,`prod-school` 因此不会在静态产物中暴露平台路由。
- "多租户与私有化同构"原则落地:私有化即单租户特例。
- `images/` 是部署镜像的单一治理来源:平台自建镜像、官方薄封装镜像和纯上游固定镜像都必须按 manifest 锁定来源、版本、digest、许可证、离线导入、安全准入和 `deploy/config/chaimir.env` 环境变量键;敏感值只由 K8s Secret/KMS 注入同名环境变量。

## 二、K8s 命名空间规划

| 命名空间 | 内容 |
| --- | --- |
| `chaimir-system` | 后端单体、前端、中间件接入 |
| `chaimir-data` | PostgreSQL、Redis、S3 对象存储、NATS、ClamAV(或外部托管) |
| `monitoring` | Prometheus、Grafana(外接) |
| `chaimir-prepull` | M2 镜像预拉取 DaemonSet |
| `sbx-*`(动态) | M2 学生沙箱(每实例一个,用后即毁) |
| `judge-*`(动态) | M3 判题沙箱(用后即毁) |
| `battle-*`(动态) | M8 对局沙箱(用后即毁) |

- **动态命名空间**由后端 ServiceAccount 负责创建/销毁;部署层维护固定最小权限 ClusterRole,独立 `chaimir-sandbox-rbac-provisioner` 只对带平台所有权标签的 `sbx-*/judge-*/battle-*/sim-*` 命名空间创建指向该固定角色的 namespaced RoleBinding;`sim-*` 只承载 M4 后端计算仿真。
- **NetworkPolicy 默认 deny-all**:动态沙箱/仿真计算命名空间间、与系统命名空间严格隔离,按需精确放行。

## 三、组件部署拓扑

```
                    ┌─────────────┐
   用户 ──HTTPS──►  │  Ingress/网关 │ ──► 前端(Nginx静态)
                    └──────┬──────┘
                           │ /api
                    ┌──────▼──────────┐
                    │ backend 单体(多副本) │ ──► PG / Redis / S3 对象存储 / NATS / ClamAV
                    │ + 模块后台任务        │
                    └──────┬──────────┘
                           │ client-go(创建/销毁动态 Pod)
              ┌────────────▼────────────┐
              │ sbx-* / judge-* / battle-* / sim-* │ (动态运行 Pod,隔离)
              └─────────────────────────┘
```

- 后端单体多副本水平扩展(无状态,会话在 Redis、JWT 无状态)。
- 沙箱 RBAC 预配器以独立无 HTTP Deployment 单副本运行,复用 backend 镜像但使用独立 ServiceAccount 和最小集群权限;后端创建动态 Namespace 后必须等待其 namespaced RoleBinding 就绪。后端集群角色只允许 `get` 固定名称 `chaimir-backend-sandbox-workload` 的 RoleBinding 作为就绪门禁,不得列举、修改或读取其他 RoleBinding。预配器不创建 Role、不持有 `escalate`,仅能 `bind` 部署层固定 ClusterRole;fail-closed 准入策略同时限制动态命名空间前缀、固定 RoleBinding 名称和固定后端主体,不得委派任意角色或主体。
- 动态沙箱销毁使用 Namespace 后台级联删除,并由后端等待 Namespace 真正消失后再完成业务状态迁移;不得对 Namespace 自身使用会残留 `foregroundDeletion` 的前台级联策略。
- 判题、撮合、回收、outbox 等后台任务当前由 server 内统一 background runner 承载;部署层不得创建没有真实入口命令的 worker Deployment。
- 动态沙箱 Pod 按需创建,受租户配额约束。

### 健康探针契约

探针的消费者是 kubelet 与网关,不是终端用户;判定信号只有 HTTP 状态码。因此后端探针是与统一文件服务下载流(`docs/总-API接口总览.md` §统一文件服务)同类的**显式非信封出口**:返回 `text/plain`,用状态码表达结果,不套 `{code,message,data,trace_id}`。业务面 `/api/v1/**` 的恒 200 信封契约不适用于探针 —— 若探针复用 `response.Fail`,依赖故障时仍返回 200,kubelet 会永远判定就绪并继续向坏副本送流量,探针形同失效。

| 路径 | 用途 | 暴露面 | 返回 |
| --- | --- | --- | --- |
| `/-/healthz` | liveness:进程是否存活,不探依赖 | 集群内(`/-/` 不在任何 Ingress path) | `200 ok` |
| `/-/readyz` | readiness:PostgreSQL / Redis / K8s API 逐个探测,超时由 `SERVER_HEALTH_TIMEOUT_SECONDS` 控制 | 集群内 | 就绪 `200 ready`;任一依赖不可用 `503 not ready` |
| `/api/healthz` | 公网最小 liveness(网关健康检查用) | 公网 | `200 ok` |

- 探针**响应体不含依赖名**;哪个依赖不可用、原始错误链只进结构化日志(含 `trace_id`),不向调用者播报内部拓扑。
- `/-/*` 不在 Ingress 任何 path 规则内,公网天然不可达;`chaimir-public-deny` 额外黑洞历史路径 `/api/readyz`。新增探针路径必须保持在 `/-/` 前缀下,不得挂到 `/api` 上。

## 四、环境分层(Kustomize)

```
deploy/
├── base/                通用 manifests(Deployment/Service/RBAC/NetworkPolicy)
├── components/          可复用 Kustomize components(验收/私有化中间件等)
├── config/              ConfigMap/Secret 模板与环境变量单一来源
└── overlays/
    ├── acceptance/      完整功能验收(生产安全基线 + 明确受控的测试数据组件)
    ├── staging/         预发布
    ├── prod-saas/       SaaS 生产(公网多租户)
    └── prod-school/     私有化(k3s,单校,关闭 platform 层)
```

- base 定义通用资源、平台服务不可变镜像引用和唯一正式入口 `www.chaimir.io`;按需 component 自己维护其资源的不可变镜像引用。overlays 只覆盖真实环境差异(副本数、外接端点、deploy_mode、是否启用平台管理员),不得复制镜像 digest 或重复声明与 `deploy/config/chaimir.env` 相同的默认值。
  前端 Deployment 由初始化容器根据 `chaimir-config` 生成 `/runtime-config.js`;禁止把 `DEPLOY_MODE` 或工具 origin
  重新作为 `VITE_*` 构建参数写入镜像,避免同一 digest 在 SaaS 与学校私有化之间漂移。
- 私有化 overlay:去掉 `/platform/*` 入口、平台级定时任务,`chaimir/migrate migrate-and-seed` 创建单校租户与首个学校管理员。
- Chaimir 自身部署清单统一走 Kustomize,不维护平台 Helm chart,避免与 base/overlays 双轨重复。
- 第三方 K8s 组件可按官方方式安装;若官方推荐 Helm,仅在需要固定 values 或交付说明时创建
  `deploy/charts/` 保存第三方 chart values,不得放 Chaimir 平台自身模板。
- 所有部署形态的密钥统一经 `deploy/config/external-secret/` 的 ExternalSecret 模板同步;包含内置中间件的形态追加 `deploy/config/external-secret-middleware/`。overlay 只覆盖 SecretStore 名称和刷新周期,禁止使用 `secretGenerator`、工作区 env 文件或命令式 Secret 作为应用注入旁路。远端密钥统一为名为 `chaimir` 的结构化对象,字段名与环境变量契约一致;SecretStore 决定其所属环境和密钥后端。
- 数据库凭据分工固定:`PG_PRIV_USER/PG_PRIV_PASSWORD` 是 PostgreSQL 属主/特权连接,仅用于中间件初始化、migration 和 M1 受控登录前跨租户定位;`PG_USER/PG_PASSWORD` 固定为 `chaimir_app` 应用角色,常规后端请求必须走该角色以确保 RLS 生效。禁止再引入单独的 owner DSN 或第二份应用角色口令。
- 后端和 `chaimir-migrate` 在建立 PostgreSQL 连接前按 `PG_STARTUP_TIMEOUT_SECONDS` 与 `PG_STARTUP_RETRY_INTERVAL_MILLISECONDS` 执行有界就绪重试,用于吸收同一批部署中数据库 Pod 已创建但尚未监听的正常启动窗口;超过时限必须保留最后一次错误并失败退出,不得无限等待或跳过迁移。
- PostgreSQL 连接池按数据库角色分开配置:`PG_APP_MAX_CONNS/PG_APP_MIN_CONNS` 仅供应用角色,`PG_PRIV_MAX_CONNS/PG_PRIV_MIN_CONNS` 仅供受控特权操作。数据库真实上限、运维预留和安全余量分别登记为 `PG_DATABASE_MAX_CONNECTIONS`、`PG_RESERVED_CONNECTIONS`、`PG_CONNECTION_SAFETY_MARGIN`,部署门禁按 `HPA maxReplicas × (应用池上限 + 特权池上限) + 运维预留 + 安全余量 ≤ 数据库上限` 校验,不得在脚本中另写默认阈值,也不得用一个共享池上限同时约束两个角色。迁移启动就绪检查固定只使用单连接,不能按应用池上限创建临时池。
- `acceptance` 使用 `APP_ENV=test` 只允许执行验收 seed 与连接受控集群内短信夹具;Cilium、gVisor、TLS、镜像签名、NetworkPolicy、Pod Security 和应用资源配置仍执行生产基线。正式交付必须使用 `APP_ENV=prod` 和公共短信网关,不得把测试夹具开关带入 staging 或生产 overlay。
- 私有运行镜像拉取凭据只以 Kubernetes `dockerconfigjson`/`dockercfg` Secret 存放在控制命名空间;后端通过 `SANDBOX_IMAGE_PULL_SECRET_NAMES` 读取 Secret 名称,由平台 K8s 层复制到 `chaimir-prepull`、动态沙箱和 M4 仿真计算命名空间。Harbor robot token 不得写入 env、Kustomize manifest、镜像层或工具 manifest。

## 五、中间件

| 中间件 | SaaS | 私有化 |
| --- | --- | --- |
| PostgreSQL | 托管/自建主从 | 单实例(可加备) |
| Redis | 托管/集群 | 单实例 |
| S3 对象存储 | 集群 | 单实例 |
| NATS | 集群 | 单实例 |
| ClamAV | 集群/托管扫描服务 | 单实例 |
| CouchDB | Fabric 富查询实验按需编排 | Fabric 富查询实验按需编排 |
| Harbor | 公网私有仓 | 校内仓 + 离线导入 |

> 私有化按校规模可单机部署全套(k3s + 单实例中间件)。
> 中间件、Prometheus/Grafana、ingress-nginx 和 CNI 的镜像来源以 `images/middleware`、`images/observability`、`images/ingress`、`images/network` manifest 为准。纯上游固定镜像不重打包,但必须按 digest 拉取、扫描、签名/准入校验并进入离线包。Harbor 是供应链启动根，固定 chart、组件源码补丁、八组件 digest 闭包和节点 OCI 预置包由 `deploy/charts/harbor/` 单独治理；它不进入 `images/image-digests.lock`，以免产生自举循环。
> ingress-nginx 统一通过官方 Helm chart 安装,chart 与控制器必须保持同一主次版本代,禁止把旧版远程静态清单与新版控制器镜像拼接部署。控制器只使用 `images/image-digests.lock` 中已完成扫描、签名和证明的 Harbor digest;admission 证书工具按 `images/ingress` manifest 的上游 digest 固定,不得使用可变 tag。

## 六、CI/CD

```
代码提交 → 路径触发(backend/frontend/images 各自流水线)
  ├─ lint + 单元测试 + 全仓源码契约审查
  ├─ 构建平台镜像(多阶段)或校验上游固定镜像 digest
  ├─ Trivy 漏洞扫描(高危阻断)+ CycloneDX SBOM
  ├─ 推 Harbor并解析不可变 digest
  ├─ Cosign 镜像签名、SBOM 证明和双重验证
  └─ 上传职责内 digest 片段
镜像元数据晋升:
  三条镜像产物流水线成功 → 串行合并 digest 片段
  → 同步 lock/base 与资源 component 的镜像引用/受控配置引用
  → 机器人 PR → 检查通过后自动合并
部署:
  已验证 digest 的机器人 PR 合入 main → 从权威锁读取全部服务 digest → 自动部署 staging
  打 tag → 从发布提交的权威锁读取全部服务 digest → 人工审批 → 部署 prod-saas
  私有化 → 生成离线镜像包 + 部署清单交付学校
```

- 文档、README、前端纯静态资源或独立镜像清单变更不得直接创建 staging Deployment；staging 自动部署只由 `images/image-digests.lock` 合入 `main` 触发,并一次校验 backend、frontend、migrate、cron 四个服务的已验证 digest 与静态 overlay 渲染结果完全一致。生产发布只消费 tag 所指提交内同一权威锁。校验通过后直接在默认加载限制下应用仓库 overlay,不得生成临时 digest overlay,也不得按 SHA tag、版本 tag 或 `latest` 猜测镜像。
- `backend` 流水线独占 backend/migrate/cron,`frontend` 流水线独占 frontend,通用 `images` 流水线不得重复构建这四个服务镜像。产物元数据只能由 `.github/workflows/image-metadata-promotion.yml` 晋升,不得由业务流水线直接改 `main`;服务自身 digest 晋升不得反向触发自身重建,只有受控共享基座 digest 变化才触发对应服务消费者重建一次。
- 全仓源码契约审查统一调用 `node scripts/audit/index.mjs`:后端流水线使用 `--source-only` 检查目录职责、路由、SDK、枚举、守卫、仿真目录和前端边界;前端流水线在构建后执行完整入口,补充打包边界检查。两条流水线不得各自复制一套规则。
- 后端流水线对 `chainassert`、哈希和雪花 ID 热点执行基准回归:使用当前提交中的同一组 `Benchmark*` 分别测量基线提交与当前提交,通过固定版本 `benchstat` 比较 `sec/op`、`B/op`、`allocs/op`,阈值由流水线环境变量 `BENCHMARK_MAX_SEC_OP_REGRESSION_PERCENT`、`BENCHMARK_MAX_BYTES_OP_REGRESSION_PERCENT`、`BENCHMARK_MAX_ALLOCS_OP_REGRESSION_PERCENT` 提供。超过阈值必须阻断,原始结果与比较结果作为流水线产物保留,不得只执行一次当前版本基准后人工判断。
- 本地源码迭代沿用同一条不可变供应链,但按变更影响集合选择性执行:仅前端源码或 `images/service/frontend` 变更构建 `service/frontend`;后端源码变更同时影响 `service/backend`、`service/migrate`、`service/cron`,而单独的服务 Dockerfile 只影响对应服务;共享 `base/go-builder`、`base/runtime-min`、`middleware/postgres` 或 `base/node-builder` digest 变化时,只重建其真实消费者。选定集合用 `images/build-images.ps1 -Images` 生成候选锁,用 `images/pull-images.ps1 -Images` 按 digest 回拉,用 `deploy/scripts/image-attestations-generate.ps1 -Images -NoEnvWrite` 完成 Trivy、SBOM、Cosign 签名/验签,再把本次已验证集合生成 digest 片段交给 `images/sync-image-metadata.ps1` 增量晋升。未选镜像保留正式锁和既有证明,不重复构建、拉取、扫描或签名;部署仍只通过 `make dev-refresh` 应用 Kustomize digest overlay。
- GitHub 托管 runner 只允许连接正式 HTTPS Harbor 与受控 Kubernetes API,`HARBOR_REGISTRY` 不得填写依赖本机 hosts/port-forward 的 `registry.chaimir.io`。只提供私网 Harbor/K8s 的交付环境必须注册同网络专用自托管 runner并使用独立标签;registry、robot、Cosign、Kubeconfig 和镜像元数据机器人凭据缺失时流水线必须在产生镜像前显式失败。

- 定时任务(CronJob):每日数据备份由 `service/cron` 镜像执行真实 `pg_dump` + S3 对象存储 对象备份,并记录入 M9 `backup_record`。业务生命周期清理留在所属模块后台任务中运行,不得在部署层保留无命令实现的占位 CronJob。

## 七、资源回收

- M2/M4/M7/M8 各自的回收逻辑为主(空闲/最长生命周期/来源级联/事件通知)。
- 资源回收由模块 service 内的后台任务统一执行并暴露 `RunXOnce(ctx)`,通过 `cmd/server/<module>.go` 接入 `platform/background`;部署层不得保留未实现的强制清理 CronJob。若后续需要集群级孤儿资源治理,必须新增真实受控运维命令、权限边界和审计设计后再接入部署清单。
- M2 快照功能要求集群安装 CSI VolumeSnapshot CRD、snapshot-controller、支持快照的 CSI 存储驱动、可用的 StorageClass 与 VolumeSnapshotClass,并在环境变量 `SANDBOX_STORAGE_CLASS_NAME`、`SANDBOX_VOLUME_SNAPSHOT_CLASS_NAME` 中显式声明;未配置或不可读取时不得启用 `snapshot_enabled`。部署层提供 `make snapshot-up` 安装官方 CSI snapshotter 的 CRD 与 controller,但不安装具体存储驱动;生产必须接入 Longhorn、Ceph RBD、云盘 CSI 等真实支持快照的存储,不得把普通 Docker volume、`rancher.io/local-path` 或演示用 hostpath CSI 当作生产快照能力。
- M2 沙箱资源用量查询要求集群安装 metrics-server 并暴露 `metrics.k8s.io`;未安装或不可读取时,后端必须返回沙箱专用错误码,不得用 Pod requests/limits 伪装成实时用量。部署层只提供 `make metrics-up`,kubelet 服务证书必须由集群 CA 签发并覆盖节点地址;任何环境都不得使用 `--kubelet-insecure-tls`。

## 八、可用性与备份

- 后端无状态多副本;中间件按形态做主从/集群(SaaS)或单实例+备份(私有化)。
- 后端收到终止信号后先将 `/-/readyz` 切换为 503,等待 `HTTP_ENDPOINT_DRAIN_SECONDS` 让服务发现摘除当前副本,再关闭 WebSocket 与 HTTP。等待窗口和 `HTTP_SHUTDOWN_TIMEOUT_SECONDS` 均来自环境配置;不得在 Deployment 中用固定 `sleep` 冒充优雅下线。
- 当前 SaaS 生产按后端单体副本水平扩展,后台任务随 server 副本运行;若后续拆独立 worker,必须先新增真实入口命令、权限边界、队列指标和部署清单,再启用队列积压 HPA。
- 备份:数据库每日全量使用 PostgreSQL 官方 `pg_dump` 自定义格式;S3 对象存储 代码/附件/报告桶对象服务端复制到备份桶;备份记录入 M9。`pg_dump` 的 stdout/stderr 分别以 `ADMIN_BACKUP_COMMAND_OUTPUT_MAX_BYTES` 做写入期硬限,避免外部工具异常输出耗尽 CronJob 内存。当前只登记全量备份能力,任何新的备份类型都必须先补齐真实策略、恢复流程和配置后再同步本文档。
- 私有化数据不出校内网,符合数据合规。

## 九、安全部署基线

- 全站 HTTPS;Ingress WAF(可选)。鉴权 Cookie 始终设置 `Secure`、`HttpOnly` 和 `SameSite`,本地开发也必须通过 HTTPS 入口访问,不提供 HTTP 降级。
- 最小权限 RBAC;后端 ServiceAccount 仅负责动态命名空间生命周期,工作负载权限由独立预配器按命名空间授予,且只允许带平台所有权标签的动态运行命名空间。
- ValidatingAdmissionPolicy 在准入层限制后端 ServiceAccount 只能管理带平台所有权标签的
  `sbx-*`/`judge-*`/`battle-*`/`sim-*` 命名空间。
- 密钥(JWT 签名、加密密钥、中间件凭据)经 K8s Secret/KMS 注入,不入镜像不入仓。
- 镜像签名校验门禁由 Sigstore policy-controller 执行。准入策略必须覆盖 canonical registry 下 `docs/总-镜像与容器设计.md` 定义的全部镜像分类,不得只覆盖平台服务或中间件而遗漏运行时、工具、基础设施及网络镜像。部署入口必须先应用 ClusterImagePolicy 并等待其 `Ready=True`,再提交受保护命名空间中的工作负载,禁止把策略对象与首批工作负载放在同一无等待的应用事务中。预拉取 DaemonSet 的一次准入请求可能包含多个镜像,部署入口必须将 webhook 超时设为不超过 Kubernetes 允许上限并保持 `failurePolicy=Fail`,不得通过缩短校验或 fail-open 绕过签名验证。平台构建镜像必须带 Cosign 签名;纯上游固定镜像必须命中 `images/` manifest 中的 digest 锁与准入策略,不得以可变 tag 绕过;
  Pod Security Restricted;高风险沙箱 gVisor/Kata 加固。
- M2 预拉取 DaemonSet 只能运行在 `chaimir-prepull` 命名空间,并使用与沙箱节点一致的 node selector/toleration。部署流程必须先在该静态命名空间创建固定名称的镜像拉取 Secret;后端 ServiceAccount 只允许对该固定 Secret 执行 `get/update`,用于校验和同步 Harbor 凭据轮换,不得获得 Secret 列表或任意名称 Secret 的读写权限。
- 预拉取和运行时接入即测都是同步等待的业务操作。`SANDBOX_PREPULL_TIMEOUT_SECONDS` 以最慢目标节点完成已发布 `CompositionSpec` 完整镜像闭包冷拉取和自检为预算,生产基线为 900 秒;`HTTP_WRITE_TIMEOUT_SECONDS` 必须严格大于该值,且必须严格大于两倍 `SANDBOX_SELFTEST_RECYCLE_TIMEOUT_SECONDS`(自检执行与清理分别计时)。配置不满足时后端启动即失败,不得让已完成的 K8s 操作因 HTTP 响应超时被误报为失败。
- **强制隔离运行时 gVisor(硬前置)**:运行不可信代码的沙箱节点池必须预装 gVisor(或等价强隔离运行时)并注册对应 K8s `RuntimeClass`,其名称配置到 `SANDBOX_RUNTIME_CLASS`;后端对所有沙箱运行时/工具 Pod 强制注入该 `runtimeClassName`,配置缺失后端启动即失败。gVisor 用户态内核同时提供内核逃逸隔离与进程数(pids)/资源约束,替代节点 kubelet 层的 `podPidsLimit`。集群未装对应 RuntimeClass 时,沙箱 Pod 无法调度——这是安全前置,不设共享内核回退。
- **CNI 强制"策略先于流量"(硬前置)**:集群必须使用 Cilium(`policy-enforcement-mode: always`)或 Calico 等在端点建立前即强制 NetworkPolicy 的 CNI,配合 M2"先建 deny-all 再建 Pod"的时序与默认拒绝出网,消除策略生效窗口。CNI 属于 `network` 镜像分类,必须按正式 Harbor digest、SBOM、Trivy、Cosign 证明部署;不得将默认 Kindnet 与第二套 CNI 并存。私有化交付清单必须核对此项。

### CNI 系统组件例外

Cilium 是集群网络控制面,不是 M2 沙箱工作负载。其 `cilium` agent 因 CNI 安装、eBPF 与节点路由职责必须使用 Chart 明确声明的宿主网络、宿主挂载与最小内核能力;这一例外只能存在于 `kube-system` 的 Cilium DaemonSet,不得复用于应用、教师工具、判题或学生沙箱。`cilium-operator` 与 `cilium-envoy` 不得继承 agent 的特权或宿主网络;Envoy 的上游 starter 因启动后主动丢弃能力而需要 root UID 时，必须在 Chart 中逐项保留其 `allowPrivilegeEscalation=false`、capability drop/add 与只读根文件系统约束，不能为了表面非 root 改坏启动链路。

平台固定 Cilium 正式发布源码版本后,`network/cilium-runtime`、`network/cilium-builder`、`network/cilium`、`network/cilium-operator` 与 `network/cilium-envoy` 必须从同一套 `images/build-images.ps1` 直接推送 Harbor `network` Project 并生成候选 digest 锁。对上游运行基座中经构建审计确认未被 Cilium 使用、但命中 HIGH/CRITICAL 的可执行文件,必须在重建配方中删除并重新扫描;不得使用 Trivy 忽略、漏洞白名单或保留旧官方镜像作为回退。仅当五个镜像均完成按 digest 回拉、Trivy、SBOM 与 Cosign 签名/验签后,才允许创建无默认 CNI 的独立验收集群并安装 Cilium。现有含 Kindnet 的集群只能保留为其他依赖环境,不得叠装 Cilium。

### Cilium 统一部署与验收基线

所有运行环境执行同一套生产 CNI 安全标准,不得因运行位置不同而使用 Kindnet、关闭策略、改成 CNI chaining 或降低验收项。任何承载 Chaimir 后端、数据中间件、判题、实验、竞赛、仿真计算或动态沙箱的集群都必须从无默认 CNI 状态安装 Cilium;已有 Kindnet 的集群不得原地叠装或继续承载平台业务。

Harbor、KMS、备份存储等可以作为集群外部依赖独立部署,其所在基础设施不属于 Chaimir 沙箱网络数据面。外部依赖不得反向承担平台业务 Pod 或学生代码运行,也不得成为绕过 Cilium NetworkPolicy 的旁路入口。迁移期间保留的旧集群只能提供外部依赖,迁移完成后必须确认其中不存在 Chaimir 业务命名空间。

Cilium Chart 统一固定为 `1.20.1@sha256:906ce40d35daad838d12add8a5ba7033e767767f51799a93c7eace2cec9cdc05`。Chart 必须把 agent、operator 与 Envoy 分别覆盖为 `images/image-digests.lock` 中的正式 Harbor digest,设置 `policyEnforcementMode=always` 与 `cni.exclusive=true`,并保留 kube-proxy;`network/cilium-runtime` 与 `network/cilium-builder` 仅是可复现构建基座,不得作为运行 Pod 部署。使用 Kind 作为集群提供者时,固定使用 `v0.32.0` 与 Kubernetes node image `v1.36.1@sha256:3489c7674813ba5d8b1a9977baea8a6e553784dab7b84759d1014dbd78f7ebd5`,创建时设置 `disableDefaultCNI: true`,并为 kubelet 启用经校验后批准的 CA 服务证书请求;这不改变任何生产安全配置或验收标准。

节点重启或地址变化后,集群入口必须核对 Pod 当前 `hostIP` 与派生 `CiliumEndpoint.status.networking.node`;仅删除节点归属失效的派生端点并等待当前 Agent 重新发布为 `ready`,不得通过保留旧 CEP、关闭策略、重建业务数据或清空节点镜像缓存绕过恢复。Cilium 恢复验收必须从当前 `CiliumNode` 读取每个节点的主机地址与健康端点地址,由每个 Kind 节点主动探测全部当前端点;不得等待可能仍保留重启前结果的后台健康缓存来代替实时数据面判断。

集群生命周期必须区分首次引导、已有环境恢复、应用刷新与非破坏停止。首次引导负责安装固定 Chart、执行真实 NetworkPolicy/gVisor 验收并部署平台;已有环境恢复只能启动或解除暂停现有节点、修复动态地址与派生端点、校验当前正式镜像和安全状态并恢复入口,不得重复执行 Helm upgrade、数据面 smoke、迁移或验收 seed;应用刷新在已有环境恢复后重新应用同一 overlay、迁移与受控验收 seed,不得借刷新重装 CNI;非破坏停止通过暂停节点容器停止 CPU 执行,保留数据库进程、volume 与 containerd 缓存,不得用短超时强制终止节点伪装成优雅停止。四种操作共享同一生产配置与安全策略,属于生命周期分工,不得演变为本地/生产双轨。

Cilium 验收只有同时满足以下条件才通过:

1. 集群中不存在 Kindnet DaemonSet 或非 Cilium CNI 配置,Cilium agent 与 Envoy 覆盖全部节点,operator 可用。
2. `cilium-config` 的策略模式为 `always`,实际运行镜像与正式 digest 锁一致,Cilium 状态无控制器失败。
3. 真实跨命名空间探测证明 deny-all 阻断、显式 ingress/egress 放行生效;测试资源用后删除。
4. Chaimir 迁移、签名准入、gVisor、运行时预拉取、实验与竞赛沙箱创建/回收均在 Cilium 集群完成。仅创建 NetworkPolicy 对象或仅通过业务 API 不得代替网络数据面验收。

静态平台网络边界同时维护 Kubernetes `NetworkPolicy` 与 Cilium 原生策略:
`chaimir-system` 控制面和 RBAC 预配器访问集群 API 时,通过 `kube-apiserver` 实体仅放行
443/6443;`chaimir-data` 的 ClamAV 仅通过 DNS 代理解析并访问
`database.clamav.net` 及其受控 CDN 别名的 443 端口,病毒库更新之外的公网出口继续保持默认拒绝。
这两类原生策略不是本地例外,所有使用 Cilium 的交付形态都必须随基础网络策略发布。
