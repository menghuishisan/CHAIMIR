## 0. 背景与总原则

- **文档驱动开发**：项目处于开发完成 + 测试阶段，本质是文档先行、代码据文档实现，文档与代码本应一致。本次整理的目标是把文档"回归统一规范（6 类 + 模块特有）"——让每份文档各司其职、前后端能据此对齐——**不是用文档去重新设计或重构代码**。
- **只改文档、不改代码**：本次及后续文档整理**不触碰业务代码**；严禁为对齐而引入"兼容代码 / 降级 shim / 兼容分支"（与 AGENTS.md §4「统一不兼容」一致，同类问题全平台只用同一种方案）。
- **对不齐 → 汇总上报，不擅自裁决**：整理中发现文档描述与已实现代码不一致（对不齐）时，**不判定哪方为真理、不擅自修改任一方**；统一汇总到一份新的《文档-代码差异清单》供用户最终裁决（改文档 or 改代码）。
- 文档的目的：让开发者/评审能按"需求 → 数据 → 接口 → 权限 → 流程 → 安全"找到对应要求，前后端据此对齐，开发不偏。
- **禁止扩散式修改**：除本规范明确授权的《文档-代码差异清单》这一份工作产物外，遇问题不许新开设计文档；改动必须回写已有文档类型。
- **整合优先**：模块"特有"内容能并入 6 类标准文档（需求/数据/接口/权限/流程/安全）的，必须并入；只有确实装不进、且信息无法被标准文档承载的，才登记为模块特有文档。禁止为"图方便"另开同主题文件。

## 1. 模块文档结构（每个模块目录 `NN-模块名/`）

每个模块**固定 6 类**文档，文件名统一前缀 `01~06`：

| 文件名 | 文档类型 | 规定职责（该写） | 明确不写（归属别处） |
| --- | --- | --- | --- |
| `01-需求规格.md` | 需求 | 业务目标、功能清单（有哪些功能/用例）、范围(in/out)、核心概念、非功能基线 | 技术方案 / 表结构 / 接口字段 / 流程 / 安全 |
| `02-数据模型.md` | 数据模型 | 本模块拥有的表/字段/类型/约束/索引/关系/RLS/状态枚举 | 接口字段 / 流程编排 / 架构推理 |
| `03-接口设计.md` | 接口设计 | 每个对外 REST/WS/RPC 的路径、方法、请求/响应**字段**、错误码、鉴权点、幂等、分页；内部 contracts 签名（前后端对齐依据） | 表结构 / 流程编排 / 安全策略细节（仅标鉴权点） |
| `04-权限矩阵.md` | 权限矩阵 | RBAC 角色 × 数据范围 × 操作权限矩阵（谁能做什么） | 鉴权实现（→安全设计/架构） |
| `05-业务流程.md` | 业务流程 | 每个核心业务的流程图/状态机（状态、转移、触发事件、异常分支），让开发不偏 | 接口字段 / 表结构（仅引枚举）/ 技术架构 |
| `06-安全设计.md` | 安全设计 | 本模块威胁模型、鉴权授权规则、输入校验、不可信隔离、数据隔离(RLS)、审计/通知调用、密钥处理；整体基线见 AGENTS.md §7，本文件只写模块特有 | 接口字段（仅标鉴权点）/ 表结构（仅标敏感标记） |

### 模块特有文档（整合优先，非自由新增）
> 原则：特有内容**能并入 6 类标准文档的，必须并入**；只有确实装不进、信息无法被标准文档承载的，才登记为模块特有文档。

- **架构设计**（M2 / M3 / M4 / M5）：引擎类模块（沙箱 / 评测 / 仿真 / 题库模板）内部分层、组件、关键技术策略、模块间契约边界(contracts)、扩展/插件点。其余模块（M1、M6–M11）无此需要，相关内容并入 `01-需求规格` 的"核心概念"或 `05-业务流程`。
- **SDK与交互协议**（仅 M4）：sim-sdk↔后端协议、确定性回放、渲染契约、内置/扩展包分流。
- **专题设计**（仅 M8）：对抗赛 / 漏洞源等竞赛专题规则。
- 其余模块如确有新类型需求，**必须先在本规范登记 scope 并授权**，再写。

### 前端页面原型（HTML 伪数据）
- 每个模块目录附 **`页面原型.html`**（按模块命名，置于 `NN-模块名/` 内）：用伪数据直观展示**该模块实际需要的前端页面**（布局、组件、交互），页面清单与该模块 `01-需求规格` 的功能清单对应。
- **只给该模块需要的页面**，不堆砌；页面以实际已实现前端为准（文档驱动，代码已实现）。
- **跨模块共享页面**（如登录认证、通知中心收件箱、个人中心等被多端复用的页面）：执行阶段据前端实际实现判定归属——若各端各自实现、语义略异，则每模块各放一份；若确为同一套共享实现，则集中放到独立的 `共享页面原型.html`（或归入 `总-前端设计规范` 引用），不重复造。
- 仅伪数据，不接真实接口。

## 3. 总（跨模块）文档

- 总-* 只做两件事：①**引用/汇总**各模块文档（如 `总-数据库表总览` 汇总各模块数据模型、`总-API接口总览` 汇总各模块接口设计）；②承载**跨模块总体规范**（技术选型、工程目录、部署、验收、前端规范、后端能力索引、开发规范）。
- 总-* **不得重复**模块文档的内部细节，只索引/汇总；模块细节以模块文档为准。
- **镜像相关只保留 1 份** `总-镜像与容器设计`（含构建规范、Harbor、私有化分发、逐镜像职责、插件化契约）。废除游离的 `总-镜像分层与能力目录.md`、`总-镜像插件化重构契约.md`，内容并入。
- `总-开发规范与要求.md`：**正式授权保留**（不并入 AGENTS.md）。定位为**跨层开发规范总纲**——承载各层规范：代码规范、注释规范、安全规范、错误处理与用户文案规范、配置与数据规范、多步骤流程持久化规范、前端规范、Git 规范等。AGENTS.md 保留"索引 + 铁律摘要"角色，详细规范指向本文件；本文件与模块 `06-安全设计` 的关系：本文件写跨层统一基线，模块文档写模块特有落地。
- 两份跟踪清单（`前端后端功能对齐清单.md`、`对齐-后端待补齐清单-2026-08-23.md`）移入 **`审查测试记录/`** 目录，与审查/测试报告同属"验证产物"，不是设计规范。**其内容不并入任何设计文档**；本规范只引用其存在。
- **验证产物不并入设计文档**：`审查测试记录/` 下所有报告（含上述两份跟踪清单）是测试期验证产物，不符合重构要求的内容保持原样留在目录内，绝不并入 总-* 或模块设计文档。

## 5. 文档修改规范（后续所有改动必须遵守）

1. **直接在源文件修改**，改完把头部 `最后更新` 改为当天日期；不新建同名/近似文件、不另开"补丁"文件。
2. 新增内容先判断归属哪个文档类型；装不进现有类型时，先修订本规范 §1/§2 登记新类型并授权，再写。
3. 相关内容归属别处时，用交叉引用（`见 docs/...`）指向，不复制。
4. 文档膨胀需"拆"时，先在本规范定义多章/多文件结构并授权。
5. 文档与代码对不齐时，**不擅自改任一方**；记入《文档-代码差异清单》由用户裁决，并标注发现日期与证据（文档位置 / 代码位置）。
