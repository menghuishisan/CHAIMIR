# Chaimir 文档治理规范

> 最后更新:2026-11-27

## 1. 当前版本与职责

文档描述当前已确认的目标、业务契约和工程约束。更新时直接替换失效正文，同步删除被替代的段落、文件及引用；同一事实只有一个权威位置，其他文档通过链接引用。文档是否保留取决于职责和有效内容，不以文件日期判断。

开发方法见[开发规范](总-开发规范与要求.md)，工程边界见[工程目录](总-工程目录设计.md)，验收条件见[验收标准](总-验收标准.md)。本文件只管理文档归属和维护方式，不重复工程规则。

## 2. 模块文档

各模块目录使用以下六类文档，编号为 01–06：

| 文件 | 职责 |
| --- | --- |
| 01-需求规格.md | 业务目标、功能范围、用例、核心概念和非功能要求 |
| 02-数据模型.md | 自有表、字段、约束、索引、关系、RLS 和状态枚举 |
| 03-接口设计.md | REST/WS/内部契约的路径、签名、请求响应、错误、鉴权点、幂等和分页 |
| 04-权限矩阵.md | 角色、数据范围与操作权限；无扩展时引用 M1 基线 |
| 05-业务流程与状态机.md | 状态转换、触发条件、编排、异常与补偿流程 |
| 06-安全设计.md | 本模块特有的威胁、隔离、校验、授权、审计和密钥边界 |

M2、M3、M4、M5 的 07-架构设计承载引擎内部分层、技术策略、契约和扩展点；M4 的 08-可视化SDK与交互协议承载 SDK、TeachingFrame、内置与扩展包协议；M8 的 07-专题设计承载对抗赛与漏洞源规则。其他内容优先归入现有六类，新增文档类型时先明确职责和索引，避免同主题并存。

模块接口文档定义字段与业务约束，不记录组件内部变量、弹窗实现、修复轮次或逐表单的通用交互规则。跨页面交互统一由[前端规范](总-前端设计规范.md)定义，模块特有任务流程归入所属业务流程。

页面原型如需维护，统一放在页面原型目录，按学生、教师、校管、平台管理和公共认证页面组织，使用伪数据；共享页面不按模块重复建设。原型不能替代正式需求、权限或接口契约。

## 3. 跨模块文档

- 平台蓝图定义总体职责；总-* 承载跨模块规范或模块索引，不复制模块内部规则。
- 数据库总览汇总模块自有表，API 总览汇总公开入口；详细字段分别由模块数据模型和接口设计维护。
- 镜像的构建、分层、逐镜像职责、分发和插件契约统一由[镜像与容器设计](总-镜像与容器设计.md)维护，部署环境由[部署架构](总-部署架构设计.md)维护。逐镜像 README 只保留独有用途、使用前提、语义约束和专项验收；能力、端口、命令、资源、探针及安全字段引用本目录 manifest，不复制机器字段或通用治理模板。项目与 SDK README 是入口，不维护第二套规范和示例。
- AGENTS.md 与另一代理入口保持一致，只保留索引和执行摘要；详细工程规则归开发规范。

## 4. 更新、合并与删除

每份正式文档必须能独立表达该主题的完整现行定义。读者不应通过对照旧正文、勘误、补充条款或历史报告，才能判断当前采用哪套规则。需求变化后继续原位维护这份定义，不为每次修复新建一份规范。

1. **确定归属。** 修改前核对本规范的职责划分、相关契约、真实调用链和最新已确认决定。同一事实只在所属文档定义；其他位置保留必要上下文和链接。公开类型、数据库迁移及生成清单已有机器权威时，文档解释业务语义、约束和来源，不手工复制整套声明。
2. **重写所属正文。** 新确认的规则直接融入对应章节，连同前提、例外、失败行为和示例一起更新。禁止保留失效定义后再追加“补充说明”“本轮修复”“以新条款为准”等纠错补丁；符合既有契约的代码修复也不产生新的事故规则。
3. **同步清理。** 全文查找同一概念的旧名称、重复定义、状态、接口、配置和示例，更新所有受影响消费者。重复内容合回权威位置；文件没有独有有效内容时删除，同时修正链接、入口索引、代码引用及当前待办。按已确认范围分阶段执行时，尚未获准修改的代码引用记录到当前状态，不为完成文档阶段越界改代码。
4. **裁定冲突。** 文档与代码冲突时，按已确认目标修正相应一方；代码存在本身不能作为改写需求的依据。有效需求、安全约束和未闭合事项不能因文档旧或实现缺失而删掉。只有缺少依据且影响业务行为或安全边界的歧义才需用户决定。
5. **保留必要证据。** 修改正文时更新日期。合并、删除前保留必要的本地恢复材料，不能覆盖其他未提交工作或丢失未闭合事项。历史版本由版本控制或本地证据追溯，不在正式正文中并排保留新旧规则。
6. **验收现行文本。** 检查全文一致性、跨文档契约、示例、链接与锚点、目录及删除影响。结构检查只能证明对应结构有效，不能代替阅读全文和语义审查；涉及实现时再按影响范围验证代码与运行结果。

文档阶段以明确清单为范围，覆盖正式文档、项目入口和其引用的说明。每份文档须完成全文阅读及职责审查；模块之间的数据归属、身份权限、状态转换、接口、事件、镜像和前端任务须完成交叉核对。遗漏、重复、失效引用及未裁定的文档矛盾清零后，才可将该阶段标为完成并进入约定的代码阶段。缺少真实环境验证的事项保留在当前验收状态，不能混写为文档矛盾，也不能据文档完成宣布业务通过。

完成结论只对应已审查的文件版本与范围；后续需求或契约变化仍按上述流程更新为最新。禁止用“以后永远不需修改”代替持续维护。

## 5. 当前状态与验证证据

审查与测试资料放在本地忽略目录审查测试记录，入口见[说明](审查测试记录/README.md)。只维护一份当前状态，更新时替换旧结论；列明剩余范围、已验证层次和必要证据引用，不持续累加每轮过程。

参赛、演示等已交付材料及其源文件属于交付快照，不作为工程规范；如需维护演示应另按交付任务更新，不从其中恢复过期架构或接口。

历史报告、截图和日志是指定源码与环境的证据，不是另一套设计规范。已被替代的报告移出文档目录，仅在本地证据目录保留可追溯副本；已闭合的旧差异与旧待办不再作为修复输入。尚未对账的历史问题保留来源和待核对状态，不擅自判为已解决，也不把旧报告的结论当成当前事实。

测试数量、修复编号、聊天原话和执行流水不写入正式设计。当前状态和历史证据必须分别标明源码检查、构建、受控测试、镜像启动、真实组合及已部署浏览器操作的结果。
