# M4 仿真可视化引擎 — 架构设计

> 核心:自描述仿真插件框架、确定性状态机、TeachingFrame 教学画面协议、封闭可视化模式、按代码来源分流的执行位置、对照推演。
> 与 M2 链插件、M3 判题器插件同一哲学:平台供框架,插件供具体。
> 最后更新:2026-08-06

## 1. 总体架构

```
┌──────────────────────────────────────────────────────────┐
│  调用方:M7 实验 / M6 教学(嵌入课时) / M3(取检查点判分)    │
│  加载(仿真包 + 初始参数 + 种子 + 来源标识)                  │
└─────────────────────────┬────────────────────────────────┘
                          │
┌─────────────────────────▼────────────────────────────────┐
│  M4 前端(React)                                           │
│  ┌──────────────┬───────────────┬─────────────────────┐  │
│  │ 内置包运行时   │ TeachingFrame  │ 通用交互渲染器        │  │
│  │ (Worker 驱动) │ (教学画面协议) │ (按声明渲染控件)      │  │
│  └──────┬───────┴───────┬───────┴──────────┬──────────┘  │
│         │ 加载/驱动       │ 渲染              │ 交互事件      │
│  ┌──────▼────────────┐   │                  │             │
│  │ 平台内置标准库      │   │  ← 快照(纯数据)   │             │
│  │ (随版本交付的 TS)  │   │     也可来自容器   │             │
│  └───────────────────┘   │                  │             │
│  叙事控制器 │ 操作序列记录器(种子+事件)│ 回放器 │ 对照推演     │
└─────────────────────────┬────────────────────────────────┘
                          │ 扩展包:每步一次快照往返
┌─────────────────────────▼────────────────────────────────┐
│  M4 后端(Go)                                             │
│  仿真包注册/审核/版本 │ 会话/序列持久化                      │
│  ┌────────────────────────────────────────────────────┐  │
│  │ 隔离执行(K8s):扩展包运行时 + 受控预览 + 重计算仿真    │  │
│  │ 独立命名空间 · deny-all · non-root · 只读根 · 硬限   │  │
│  └────────────────────────────────────────────────────┘  │
└───────────────────────────────────────────────────────────┘
```

**关键**:执行位置按**代码来源**分流,不按作者偏好选择 —— 平台内置标准库(随版本交付的 TypeScript,与后端 Go 同等信任级别)在浏览器 Worker 内运行,零延迟、秒开、可离线;教师与第三方提交的扩展包一律在后端隔离容器内运行,浏览器**只渲染容器返回的纯数据快照,不执行任何第三方代码**。详见 §8。

## 2. 自描述仿真插件框架(核心)

### 2.1 仿真包结构

一个仿真包 = 自描述四件事(详 §3~§6):

```
SimPackage {
  meta:         { code, name, category, version, entry? }
  state:        初始状态结构 + reducer(state, event, tick) → newState   // 确定性
  interactions: InteractionDef[]   // 声明式交互列表(通用,见 §4)
  render:       (state) → TeachingFrame  // 声明当前教学画面
  narrative?:   NarrativeStep[]     // 可选教学叙事
}
```

`meta` 里**没有 `compute`**:执行位置由后端按作者类型派生(内置=浏览器 Worker、教师/第三方=隔离容器,见 §8),
不是作者可声明的字段 —— 让作者写它只会产生「声明了一个平台无法运行的执行位置」这类无效状态。
`entry` 只对扩展包有意义(归档内的入口模块路径,供隔离容器装配);内置包由 registry 按 code 装配,故省略。

### 2.2 与平台的契约

- 平台提供:运行时(加载+驱动)、TeachingFrame 解释器、封闭模式渲染器、交互渲染器(控件)、生命周期(审核上架)。
- 仿真包遵守:reducer 必须是**纯函数**(同输入同输出),render 必须只输出 TeachingFrame 纯数据,interactions 必须声明完整。
- 新仿真 = 写一个包 + 审核上架,**平台代码零改动**。

## 3. 确定性状态机

### 3.1 模型

```
状态演化:  newState = reducer(state, event, tick)
事件来源:  ① tick 推进(时间)  ② 学生/教师交互(注入事件)
随机:      种子化 PRNG,seed 固定 → 演化唯一
```

### 3.2 确定性的红利

| 能力 | 实现 |
| --- | --- |
| 单步回退 | 从初始 + 种子重算到 tick-1(不存状态快照) |
| 回放 | 重放 `(seed, event[])` |
| 分享剧本 | 导出 `(seed, event[])`,他人复现 |
| M3 判分 | 检查点读确定状态;操作序列可复现核验 |

> 用"存操作序列"替代旧版"存状态快照",轻量且天然支持回放/分享。

## 4. 通用交互协议(彻底不固定)

### 4.1 InteractionDef 声明

```
InteractionDef {
  id, kind,            // kind: button|slider|hold|select-element|drag|form
  params: FieldDef[],  // 任意字段 + 约束(范围/枚举/默认)
  target: "global"|"element",
  available_when?,     // 状态/阶段条件
  label_tag?           // normal|recover|perturb|attack(仅视觉:配色+二次确认)
  emits: eventType     // 触发后注入的事件类型
}
```

### 4.2 通用交互渲染器

平台按 `kind` + `params` **自动渲染控件**,无需仿真写 UI:

| kind | 渲染 |
| --- | --- |
| button | 按钮,点击 emit 事件 |
| slider | 滑块调参(FieldDef range) |
| hold | 按住持续 emit(如持续 spam 交易) |
| select-element | 先点选画布元素,再施加操作 |
| drag | 拖拽(如连线、移动) |
| form | 字段表单提交 |

→ 任意仿真声明任意交互都能直接用;攻击只是 `label_tag=attack` 的普通交互。

## 5. TeachingFrame 教学画面协议(核心)

> 这是 M4 的稳定底层框架。仿真包不是输出一堆可视化组件,而是输出“这一刻学生应该怎么看”的教学画面。平台负责把教学画面解释成主舞台、右侧辅助区、底部时间控制和统一动画。

### 5.1 为什么不是旧版区域布局协议

旧版区域布局协议只回答“有哪些模式、放在哪里”,无法表达“学生当前应该关注谁、历史消息何时淡出、为什么这一阶段重要”。结果很容易出现新旧步骤全部堆叠、图边越来越多、右侧信息拥挤等问题。

M4 改为 `TeachingFrame`:状态机每次 render 输出当前教学画面。画面必须同时声明:

- 当前阶段是什么,学生此刻要观察什么。
- 哪个模式是主可视化,哪些模式只是证据、时间线、指标或追踪。
- 哪些元素是焦点、上下文、历史或应淡化对象。
- 模式数据仍然只使用平台维护的七类封闭模式。

### 5.2 TeachingFrame 结构

```typescript
interface SimPackage {
  render: (state) => TeachingFrame;
}

interface TeachingFrame {
  summary: string;
  phase: FramePhase;
  focus: FrameFocus;
  layout: FrameLayout;
  patterns: VisualPattern[];
  annotations?: FrameAnnotation[];
}

interface FramePhase {
  id: string;
  title: string;
  intent: "observe" | "compare" | "verify" | "debug" | "attack" | "recover" | "replay";
  // 只有两段(前端规范 §7.2 B):focus 已用舞台高亮指出该看哪个元素,不设「看哪里」
  explanation: {
    what: string;   // 当前发生什么
    why: string;    // 为什么重要
  };
}

interface FrameFocus {
  primary: string[];    // 本帧核心对象
  secondary?: string[]; // 辅助观察对象
  muted?: string[];     // 保留但降低视觉权重的对象
}

interface FrameLayout {
  primary: string;       // 主舞台 pattern id
  evidence?: string[];   // 右侧证据 pattern id
  timeline?: string;     // 右侧或底部时间证据 pattern id
  metrics?: string[];    // 右侧指标 pattern id
  trace?: string;        // 代码追踪锚点
  checkpoints?: string[];// 检查点锚点
}
```

### 5.3 元素生命周期

每个模式内可渲染元素都可以携带统一生命周期,平台用它控制动画、淡出、历史保留和无障碍描述。生命周期不是前端兜底过滤,而是算法视图的教学语义输出。

```typescript
interface VisualElementMeta {
  id: string;
  label: string;
  role?: string;
  lifecycle: {
    state: "entering" | "active" | "settled" | "leaving" | "archived";
    fromTick: number;
    toTick?: number;
  };
  emphasis: "focus" | "context" | "history" | "ghost";
  explanation?: string;
}
```

要求:

- 正在发生的消息、投票、区块、证明路径必须是 `active/focus`。
- 已完成但仍有教学价值的对象使用 `settled/history`。
- 不再参与本阶段判断的对象使用 `archived/ghost`,由平台统一淡化或折叠。
- 不允许算法把所有历史边、历史消息无差别塞进主视图。

### 5.4 封闭可视化模式集

区块链教学可视化的具体算法不同,但可视化骨架稳定收敛为七类。`VisualPattern` 是 TeachingFrame 的材料,不再携带页面区域字段。

```typescript
interface VisualPattern {
  id: string;
  mode: "graph" | "chain" | "tree" | "matrix" | "pipeline" | "lane" | "chart";
  title: string;
  data: unknown;
}
```

| 模式 | 骨架 | 覆盖的仿真类型 |
| --- | --- | --- |
| 图网络 Graph | 节点 + 边 + 消息过程 | P2P 网络、共识节点、状态机、拓扑 |
| 链式 Chain | 线性/分叉的块序列 | 区块链、最长链、分叉、双花、自私挖矿 |
| 树形 Tree | 树结构 + 路径 | Merkle Tree、MPT、证明路径 |
| 矩阵 Matrix | 网格单元 | 投票矩阵、校验矩阵、权限矩阵 |
| 流水线 Pipeline | 分步数据流 | 哈希、签名、交易生命周期、EVM 执行 |
| 时序泳道 Lane | 多方时间轴消息 | PBFT、跨链消息、中继、调用栈 |
| 图表 Chart | 数值趋势 | 算力、质押权重、gas、价格、延迟 |

### 5.5 两条架构红线

**红线一:封闭模式集 + 严进扩展闸门**
- 仿真作者只能组合平台封闭模式,不能自带渲染器。
- 确需新模式时,走平台级评审;通过后成为所有仿真的公共资产。

**红线二:作者给教学语义,平台负责表现**
- 作者输出阶段、焦点、布局意图、元素生命周期和模式语义数据。
- 布局、绘制、动画、响应式、无障碍由平台统一处理。
- 优化某个模式或 TeachingFrame 解释器时,所有内置包、教师包和第三方包自动受益。

### 5.6 模式组合示例

PBFT 不是“固定页面模板”,而是一组面向当前阶段的教学画面:

```typescript
render(state) => ({
  summary: "Prepare 阶段正在收集 2f+1 票",
  phase: {
    id: "prepare",
    title: "Prepare 投票",
    intent: "verify",
    explanation: {
      what: "副本节点广播 Prepare 消息。",
      why: "节点需要确认同一请求已被足够多副本接受。"
    }
  },
  focus: {
    primary: ["prepare-n1-n2", "prepare-n1-n3"],
    secondary: ["node-1", "node-2", "node-3"],
    muted: ["pre-prepare-old"]
  },
  layout: {
    primary: "pbft-graph",
    evidence: ["pbft-vote-matrix"],
    timeline: "pbft-lane"
  },
  patterns: [
    { id: "pbft-graph", mode: "graph", title: "副本消息传播", data: graphData },
    { id: "pbft-lane", mode: "lane", title: "三阶段消息时序", data: laneData },
    { id: "pbft-vote-matrix", mode: "matrix", title: "Prepare/Commit 投票矩阵", data: matrixData }
  ]
})
```

这里平台不会猜“第一个 pattern 是主视图”,也不会从模式自身推断布局;主舞台和辅助区完全由 `layout` 明确声明。

## 6. 教学叙事层(可选)

```
NarrativeStep {
  trigger,             // 到某 tick / 某状态 / 学生操作后
  highlight?,          // 高亮哪些状态元素
```

## 7. 对照推演(轻量,替代旧版复杂联动)

学生的真实问题是「**我这一步造成的,还是算法本来就会这样**」。平台的确定性保证让这件事可以变成受控实验:
固定 seed 与初始参数,只让「有没有干预」这一个变量不同,两条过程的差别就只能由干预解释。

- **对照推演**:同一仿真包起两个独立会话,**同一 seed、同一初始参数**,共用一个播放时钟同步推进。
  对照组只消费自动推进(算法自己跑),干预组额外消费学生的全部操作(注入攻击、扰动、调参)。
- **呈现口径**:舞台仍是**全尺寸单幅**,A/B 一键切换谁在台上;底部差异条按**当前时刻**逐键列出两侧
  `metrics` 与 `checkpointValues` 的差异。不做并排双舞台 —— 半屏放不下 graph/matrix/lane 这类密集模式,
  而人也盯不住两个同时演化的动画;差异恰恰不在画面里、在数字里。
- **通用而非逐包适配**:差异条只读协议已强制的扁平 `metrics`(`Record<string, number|string|boolean>`)
  与 `checkpointValues`,任何包都能对照,不为单个包写专用对比视图。
- 不做旧版跨画布因果弧线、owner 共享状态空间:两个会话各自持有自己的 seed、params 与 events,不共享状态。

边界:

- **只对平台内置包提供**。扩展包在隔离容器内运行,对照要两个会话即两个 Pod,成本翻倍而教学价值不变。
- **只在无会话的自由推演里提供**。带会话时服务端记录是只追加的操作序列,表达不了「对照组的推进」,
  混入会与已有条目撞号 —— 与「回退即脱离记录」同一条道理。
- **多仿真同屏(不同包并排)明确不做**,见 01 需求规格 §8:不同算法不共享 tick 语义、参数与状态,
  并排看不出任何关系;工作台是深链,需要时开两个浏览器标签页即可,平台不为此再做一套分屏壳。

## 8. 执行位置按代码来源分流

| 包来源 | 运行位置 | 浏览器职责 | 理由 |
| --- | --- | --- | --- |
| 平台内置标准库(`builtin__`,7 类 41 个) | 浏览器 Worker | 在 Worker 内跑 `initState`/`reducer`/`render` | 随平台版本交付的 TypeScript,与后端 Go 同等信任级别;零延迟、秒开、可离线、不占服务器算力 |
| 教师扩展包(`teacher_<id>__`)、第三方扩展包(`org_<id>__`) | 后端隔离容器 | **只渲染容器返回的纯数据快照,不执行任何第三方代码** | 外部提交的可执行代码不得进入平台 origin,详见 06-安全设计.md §2 |
| 少数重计算仿真(平台运维登记的算法能力) | 后端隔离容器 | 同上 | 计算量超出浏览器承受范围 |

**分流依据是代码来源,不是作者偏好**:`compute` 由后端按 `author_type` 派生 —— 内置包恒为 `browser`,
教师与第三方提交恒为 `isolated`,提交请求结构中不含 `compute` 与 `backend_adapter` 字段(与 `author_type`、
`teacher_<id>__` 前缀同为服务端强制)。这消掉了「提交了一个 `compute=browser` 的扩展包但没有任何路径能运行它」
这一整类无效状态。

协议一致 → 两个执行位置对仿真作者透明:`initState`/`reducer`/`render` 签名相同、`TeachingFrame` 相同、
交互声明相同,作者不为「跑在哪」写第二套实现。

**扩展包返回完整快照而非仅状态**:`render` 是仿真包自己的函数,扩展包的 `render` 属外部代码,
浏览器不得执行。因此隔离容器返回的是 `{ tick, state, view, currentStep, interactionAvailability, checkpointResults }`
完整快照,浏览器交给平台自己的 TeachingFrame 解释器与封闭模式渲染器绘制。前端因此**只有一条渲染路径**,
不存在第二条执行路径,也不在页面复制 reducer、舞台、时间线或检查器。

**容器输出是不可信输入**:快照来自不可信容器,后端必须按 TeachingFrame 协议校验后才转发 ——
`patterns` 只能是 1 到 3 个带稳定 `id` 的封闭模式,`mode` 只能取七类平台模式,`layout` 只能引用当帧存在的
pattern `id`,`state.nodes` 等规模字段受包声明 `scale_limit` 约束。这套规则与前端 `assertValidTeachingFrame`
等价,但**后端必须自己有一份**,不能把校验只放在前端。

### 8.1 隔离执行边界

为遵守《工程目录设计》§3.1.1 的同层互不依赖规则,M4 不直接调用 M2 沙箱接口,只复用 `internal/platform/k8s`
客户端,不得 import 或调用 `internal/modules/sandbox`,也禁止把 M2 的沙箱 WorkloadSpec 当作 M4 后端计算入口。
需要与真实链沙箱联动的数据由 M7 在业务编排层采集后作为输入事件或初始参数传给 M4。

两类隔离执行共用同一套 K8s 编排(独立命名空间、deny-all NetworkPolicy、non-root、只读根文件系统、
丢弃全部 Linux capabilities、禁用 ServiceAccount Token、RuntimeDefault seccomp、requests/limits、
就绪等待与单次执行超时),差别只在镜像与投递方式:

| 能力 | 镜像 | bundle 投递 | 用途 |
| --- | --- | --- | --- |
| `sim-package-runner` | `sim/package-runner` | 会话建立时经 k8s exec **stdin** 推入归档字节,容器内校验 sha256 与 `bundle_hash` 一致后装配 | 扩展包运行时 + 受控预览 |

同协议的第二类接入形态是「算法固化在镜像内」的重计算能力(`sim/<package-code>`,无 `entry`、不投递 bundle):
适配器对它已完整支持,但**当前部署不登记任何一项** —— `sim_package` 的复合 CHECK 把作者类型、执行位置与
装配方式绑成一条,平台登记 + 无 `entry` + 有运行能力这一组合落不进任何一支,也没有写入路径会创建它。
它是明确不做的形态,启用条件见 `docs/前端后端功能对齐清单.md` §6.26;`images/sim/graph-layout` 保留为该形态的接入示例。

**为什么 bundle 走 exec stdin 而不是让容器自己下载**:计算 Pod 根文件系统只读且网络 deny-all,
容器既写不下也取不到对象存储正文;而放开网络就等于把隔离边界拆掉。经 exec stdin 投递不触碰网络策略,
deny-all 保持完整,且字节由后端从统一文件服务取出后直接推入,容器全程不持有任何凭据。
归档落在容器内唯一可写的 `emptyDir`,随命名空间删除一并消失。

能力目录仍由部署配置 `SIM_BACKEND_STDIO_ADAPTERS_JSON` 唯一登记:镜像、无 shell 命令、受控环境变量、
资源 requests/limits、超时和 I/O 上限只来自该配置,并在应用启动时完成严格 JSON、Kubernetes quantity、
能力编号唯一性、digest 证明与命令边界校验。能力环境变量不得包含密码、token、私钥或其他凭据。
适配器不接受包级 `backend_config`;`scale_limit(nodes/max_tick/max_events)` 由已审核仿真包提供,
统一限制状态节点规模与单会话执行步数,不得另建一套阈值。

### 8.2 租户并发上限

一个会话一个 Pod,因此扩展包仿真必须有并发闸门,否则一个班同时进入即数十个 Pod,循环建会话可耗尽节点。
`SIM_BACKEND_MAX_CONCURRENT_SESSIONS_PER_TENANT` 限定单租户同时活跃的隔离执行会话数,超限返回 `42005`。
上限来自部署配置,不硬编码;匿名公开回放不建立隔离执行会话(见 03-接口设计.md §2.2),因此无从借它耗尽资源。

### 8.3 扩展规则与生产约束

适配器按执行协议复用,算法按镜像隔离。新增同为 `stdio-json` 的重计算算法时,只能新增 `sim/<package-code>`
镜像、manifest、digest 证明、能力目录项和对应 `sim_package`,不得复制 Go 适配器或 Kubernetes 编排代码;
只有协议和生命周期确实不同才新增 `BackendAdapter` 实现。

`compute=isolated` 不是降级为前端运行或空回显的兼容开关。提交、审核通过、重新上架与 WS 连接都必须命中注册表
并通过适配器配置校验,否则统一返回后端计算不可用或包参数无效;未注册真实适配器时不得把后端计算降级为空实现,
也不得让扩展包回落到浏览器执行。
