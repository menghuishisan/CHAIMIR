# M4 仿真可视化引擎 — 安全设计

> M4 运行第三方/教师提交的仿真包(代码)。本文覆盖:执行位置分流、隔离边界、审核、数据隔离。
> 最后更新:2026-08-06

---

## 1. 核心风险

仿真包是**外部提交的可执行代码**,主要风险:
- 恶意代码:窃取 token、发恶意请求、挖矿、XSS。
- 不稳定代码:死循环、内存泄漏、卡死浏览器。
- 不纯 reducer:破坏确定性,导致回放/判分不一致。
- 资源耗尽:循环创建执行会话占满集群。

---

## 2. 执行位置分流(第一道也是最根本的边界)

**外部提交的代码不在浏览器里执行**,连隔离 Worker 也不用。执行位置按代码来源分流(见 02 架构设计 §8):

| 包来源 | 执行位置 | 浏览器职责 |
| --- | --- | --- |
| 平台内置标准库(`builtin__`) | 浏览器 Worker | 在 Worker 内跑 `initState`/`reducer`/`render` |
| 教师/第三方扩展包 | 后端隔离容器 | **只渲染容器返回的纯数据快照,不执行任何第三方代码** |

**为什么不用浏览器 Worker 承载扩展包**:平台 Worker 在启动第一时间就调 `installRuntimeGuards()`,
封禁 `fetch`/`XMLHttpRequest`/`WebSocket`/`EventSource`/`Worker`/`importScripts`/`eval`/`Function`/
`indexedDB`/`caches`/`Math.random`/`Date.now` 等能力 —— 之后进入的代码已在笼子里。
但要装配外部 bundle 就必须**先解封动态 import**,这意味着第三方模块的顶层代码会在**未封锁的 Worker 内执行一次**,
且身处平台自己的 origin:它能拿路径受限 Cookie 去打平台自身接口,也能 `importScripts` 同源资产,
`connect-src 'self'` 挡不住这类同源行为。同理,让浏览器执行扩展包的 `render` 也是把外部代码放进 origin。
因此扩展包一律在容器内执行,**前端 CSP 保持 `script-src 'self'`,不放开 `blob:` 或 `unsafe-eval`**,
`installRuntimeGuards` 的「启动即封锁」不为任何场景让路。

内置包在浏览器执行的依据不是"信任仿真代码",而是它**就是平台代码**:随版本交付的 TypeScript,
与后端 Go 同一仓库、同一评审、同一发布链路,不存在"外部提交"这个前提。

其余前端侧约束(对两类包同时生效):

- **渲染消息化**:仿真产出 `TeachingFrame`(纯数据),由平台可信解释器和封闭模式渲染器绘制;
  仿真代码**不直接操作画布/DOM**。
- **CSP 加固**:落点是前端静态服务的 `images/service/frontend/security-headers.conf`(唯一定义处,
  由 nginx 每个 location 显式 include —— nginx 的 `add_header` 不做继承,子 location 一旦自带 header
  就会丢掉父级全部 header)。关键指令:`script-src 'self'`、`worker-src 'self'`、`connect-src 'self'`、
  `object-src 'none'`、`frame-src 'self'`;产物零内联脚本、零 `eval`,内置仿真与 Monaco 的 Worker
  均为同源 `/assets/*.js`。

## 3. 隔离容器边界(扩展包与重计算仿真)

两类隔离执行共用同一套 K8s 编排,差别只在镜像与 bundle 投递方式(见 02 架构设计 §8.1):

- 独立命名空间(按会话)、deny-all NetworkPolicy(Ingress + Egress)、non-root、只读根文件系统、
  禁止提权、丢弃全部 Linux capabilities、禁用 ServiceAccount Token、RuntimeDefault seccomp、
  `pod-security.kubernetes.io/enforce=restricted`、requests/limits;输入、输出、图规模、
  就绪等待与单次执行均有部署上限。断线、失败、归档均删除会话命名空间。
- 镜像必须以完整 digest 命中 Cosign/Trivy 证明清单,命令不经 shell,环境变量只来自部署配置
  且凭据语义键在启动时被拒绝。未登记能力返回 `42005`,不得用空实现、回显实现或伪适配器冒充生产路径。
- **bundle 经 k8s exec stdin 投递**:计算 Pod 根文件系统只读且网络 deny-all,容器既写不下也取不到
  对象存储正文;放开网络就等于拆掉隔离边界。字节由后端从统一文件服务取出后直接推入容器标准输入,
  容器内先校验 sha256 与 `bundle_hash` 一致再装配,**容器全程不持有任何凭据**。
  归档落在容器内唯一可写的 `emptyDir`,随命名空间删除一并消失。
- **容器输出是不可信输入**:返回的快照必须由后端按 TeachingFrame 协议校验后才转发 ——
  `patterns` 1 到 3 个且带稳定 `id`,`mode` 只取七类平台模式,`layout` 只引用当帧存在的 pattern `id`,
  规模字段受包声明 `scale_limit` 约束。这套规则与前端 `assertValidTeachingFrame` 等价,
  但**后端必须自己有一份**,不得把校验只放在前端。
- **租户并发上限**:一个会话一个 Pod,`SIM_BACKEND_MAX_CONCURRENT_SESSIONS_PER_TENANT` 限定
  单租户同时活跃的隔离执行会话数,超限返回 `42005`。没有这道闸门,一个班同时进入即数十个 Pod,
  循环建会话可耗尽节点。匿名公开回放不建立隔离执行会话,因此无从借它耗尽资源。
- M4 不直接调用 M2 沙箱接口,避免同层模块互相依赖;真实链沙箱数据由 M7 等上层编排后作为输入事件传入。
- 与平台核心服务、其他租户数据隔离;确定性与超时约束与前端一致。

## 4. 资源与稳定性保护

- **执行超时**:内置包单次 Worker 命令设超时,超时终止该 Worker 并提示仿真异常。阈值从
  `deploy/config/chaimir.env` 的 `SIM_WORKER_COMMAND_TIMEOUT_MS` 注入前端装配层,
  再作为 `workerCommandTimeoutMs` 传入 `sim-sdk`,不得在 SDK 内写死生产阈值。
  扩展包单次容器执行超时由能力目录的 `ExecTimeoutSeconds` 控制。
- **规模上限**:仿真包声明 `scale_limit`(节点数/max_tick/max_events),两个执行位置都强制;超限拒绝。
- **内存监控**:Worker 内存异常增长则熔断,防卡死浏览器;容器侧由 requests/limits 硬限。
- **确定性校验**:审核时在隔离容器内用同 seed 跑两遍比对结果,reducer 非纯函数(结果不一致)则拒绝上架。

## 5. 仿真包审核

上架前必经,且**审核本身就在隔离容器内执行** —— "跑起来看效果对不对"这件事需要一个能安全执行第三方代码的地方,
那个地方与生产运行时是同一套设施(见 06 业务流程 §4):

- **隔离预览**:在与生产同构的隔离容器内装配并运行仿真包,产出 `worker_preview` 与若干**样例教学帧**。
- **确定性测试**:同 seed 同参数跑两遍,逐帧比对,产出 `determinism_check`。
- **人工判断效果**:自动校验回答"能不能跑、是否确定性",回答不了"这个 PBFT 实现对不对"。
  故预览报告必须携带容器渲出的样例帧,让平台管理员有具体内容可看,而不是只看两个 `passed` 徽章。
- **静态扫描**:扫描包代码危险调用模式,命中即在报告中标注。**它是给审核人的信号,不是隔离边界** ——
  正则拦不住 `globalThis['fe'+'tch']` 这类拼接,动态语言下的能力访问无法靠模式匹配穷尽。
  真正的边界是容器隔离(§3),扫描只用于把可疑包提请人工重点查看。
- **TeachingFrame 协议校验**:manifest 必须声明 `render.protocol=teaching-frame`;预览必须校验每帧含
  `summary/phase/focus/layout/patterns`,且 `layout` 只引用当前帧存在的封闭模式 ID。
- **命名空间**:教师/第三方包强制 `teacher_<id>__` / `org_<id>__` 前缀,防覆盖内置包。
  教师入口的 `author_type`、`author_id` 与 `compute` 由服务端身份派生 —— 提交请求结构中不含
  `compute` 与 `backend_adapter` 字段,不得接受客户端传入值伪造平台内置或第三方命名空间、
  或声明一个没有任何路径能运行的执行位置。
- **版本不可变**:已上架版本内容不可改,修改须发新版本(保证已用实验稳定)。
- **审核门禁归后端控制**:上传阶段由后端写入 `bundle_hash`、`metadata_validation`、`static_scan`;
  隔离预览经内部服务签名补充 `determinism_check`、`worker_preview` 及样例帧,平台管理员不得手工伪造预览结果。
  审核通过时必须重新校验报告中的 hash 与 `sim_package.bundle_hash` 一致,且四项均为 `passed`,
  不能信任调用方临时提交的 validation report。
- **预览数据最小可见**:`GET /packages/{id}/preview` 仅允许包作者读取自己的待审报告;
  平台管理员通过审核列表读取。任意教师/学校管理员不得通过猜测 id 读取其他作者 pending review 数据。

## 6. 数据与多租户

- 仿真会话/操作序列带 `tenant_id` + RLS,跨租户不可见。
- 操作上报接口校验会话归属(owner/source_ref 对应租户与用户),防越权写他人会话。内部单会话回收、批量回收和检查点上报必须校验已验签服务请求中的 `source_ref` 与目标会话一致,禁止合法内部调用者篡改其他来源会话。
- 分享剧本:分享码不含敏感信息,仅含 `package+version+seed+params+actions`;跨租户复现仅复制公开仿真逻辑,不泄露数据。**匿名公开回放只运行平台内置包** —— 既因扩展包 bundle 属所属租户教学资产(分享码不得成为跨租户取包凭据),也因匿名请求不得触发隔离容器创建(那是零成本资源耗尽入口)。
- 检查点上报只保存学生作答/达成结果快照,不保存正确答案;正确答案和判分规则仍由 M5/M3 管理。
- 包审核通过/退回、上下架、会话创建/归档等敏感生命周期动作必须写入 M1 统一 `audit_log`;模块内 `sim_action_log` 只保存仿真交互序列,不得替代审计。

## 7. 安全测试要点

- 扩展包不得在浏览器上下文获得任何执行机会:前端对非内置包只渲染服务端快照,不装配 bundle、不建 Worker。
- 扩展包尝试访问网络/凭据/宿主文件系统必须被容器 deny-all、只读根文件系统与无凭据环境阻断。
- 内置仿真包尝试访问 DOM/cookie/token/网络必须被 Worker 运行时封锁 + CSP 阻断。
- 恶意/死循环仿真被超时与资源熔断,不影响页面与其他仿真。
- 非纯 reducer(破坏确定性)在隔离预览期被拒。
- 容器返回的非法教学帧(越界 pattern 数、未登记 mode、悬空 layout 引用、超规模状态)必须被后端拒绝。
- 单租户超过并发上限后新建执行会话被拒,已有会话不受影响。
- 越权上报/读取他人会话被拒。
- 内置包 code 不可被教师扩展包覆盖。
