## 一、核对方法(可复现)

不靠人工比对,用三段脚本机械提取后交叉核对:

1. **后端路由表**:遍历 `backend/internal/modules` 与 `internal/platform` 的全部 `.go`,
   解析 `*.Group(...)` 前缀链与 `.GET/.POST/.PATCH/.PUT/.DELETE(...)` 注册点。
   难点两处,都已处理:子路由多写成 `registerXxx(g gin.IRouter)`,函数入参名与顶层组变量重名
   (直接按名字查前缀会把 `/platform` 组算到根前缀上);服务间路由的组是**内联实参**
   `api.registerInternalRoutes(g.Group("/internal", authn.ServiceMiddleware()))`,不落成变量。
   两处不处理会分别少算 `/platform` 段与整个 `/internal` 段。
2. **api-client 方法表**:解析 `frontend/packages/api-client/src/modules/*.ts` 的方法与请求路径。
   verb 必须含 `postFormData` / `patchFormData` / `getAttachment` / `wsURL` / `upload` 这些包装 ——
   只认 `get/post` 会把「上传、取件、WebSocket」类接口误报成前端没封装(初版就误报了 33 条)。
3. **页面调用**:在 `frontend/apps/web/src` 与 `packages/ide`、`packages/api-client`(内部转调)
   里搜每个方法名的调用点。

路径比对前统一规范化:去 `/api/v1` 前缀、`:param` 与 `${expr}` 都归一成 `{}`。

## 六、下一轮前端必须接入的最终契约

本节是前端冻结解除后的改造清单,不是后端兼容层。前端只能切换到以下最终接口,
不保留旧的大页筛单、当前页切片统计或客户端二次筛选作为备用路径。

> **2026-08-24 状态**:本节 6.1–6.3 前端已全部接入(落点见第四节),
> 6.4 属后端/镜像侧,前端只展示后端状态。接入中新暴露的缺口见第九节。

### 6.1 详情页单读

| 页面 | 最终请求 | 处理要求 |
| --- | --- | --- |
| 教师实验详情/编辑 | `experiment.getExperiment(id)` | 深链首屏直接读取;编辑提交继续携带服务端返回的版本字段 |
| 教师竞赛详情/运营 | `contest.getContest(id)` | 详情、发布、运营动作均以单读返回对象为当前版本 |
| 平台运行时详情 | `sandbox.getRuntime(id)` | 同时展示 `status`、`selftest_status`、`adapter_spec` 摘要和不可部署原因;未通过自检不得显示可启用状态 |

### 6.2 筛选与全量指标

列表筛选值直接映射后端参数:
`level`、`is_locked`、`is_late`、`is_shared`、`prevalidate_status`。
请求变化后重新从服务端取 `items`、`total` 和 `facets`,不能从当前页推算总数或分布。

固定聚合读取位置如下:

| 页面 | 字段 |
| --- | --- |
| 平台审计 | `data.facets.action` |
| 教师试卷 | `data.facets.gen_mode` |
| 学生实验 | `data.facets.collab_mode`、`data.facets.require_report` |

空数据统一按 0 展示;没有该列表聚合契约的接口不得自行猜测 `facets`。

### 6.3 镜像与编排页面

平台运行时、工具和判题器页面必须区分以下状态,不能把“镜像已拉取/Pod Ready”当作可用:

- 镜像证明与预拉取状态:只说明供应链和节点缓存状态;
- 运行时接入自检:必须显示 `selftest_status` 与用户向失败原因;
- 运行时 `status=onboarding` 或判题器 `status=disabled`:禁止出现在可选组件列表;
- `runtime_config_required=true` 的工具:只有组合快照生成真实配置后才允许进入可部署状态;
- 组合编辑页只提交声明式组件、参数和 `links`;高级视图只读展示编译后的 WorkloadSpec、资源、端口、网络策略和挂载;
  不允许前端编辑镜像地址、digest、启动命令或安全上下文。

### 6.4 不能由前端补齐的能力

14 个运行时的原生操作、12 个工具的真实核心操作和 4 个镜像判题器的自检/下游评测,
必须由镜像 manifest、平台目录适配器和真实沙箱执行共同证明。前端只能展示后端状态,
不能通过隐藏按钮、默认勾选、静态成功文案或直接调用内部接口绕过接入门禁。

## 七、实验、竞赛与镜像编排剩余实现项

本节记录前端冻结期间必须由后端、镜像和部署侧完成的最终单轨实现。以下项目不能用镜像已登记、供应链扫描通过、预拉取成功或 Pod Ready 代替。

### 7.1 发布快照冻结完整可执行规格

组合发布时必须冻结运行时、工具和基础设施的完整 WorkloadSpec、镜像 digest、端口、资源、挂载、NetworkPolicy、Secret 引用和自检契约。实验启动、竞赛环境创建、漏洞预验证、判题、暂停恢复和重建只能消费已发布快照，并校验完整快照摘要；不得在启动时按当前目录重新编译旧定义。

该能力复用现有 JSONB 字段，不新增表、不保留旧摘要兼容分支。镜像或组件规格升级必须产生新快照，不能静默改变已发布实验或赛题的执行内容。

### 7.2 基础设施进入统一组件目录

`images/infra` 与 `images/tool` 都属于教师可声明或编译器按依赖自动展开的沙箱组件。基础设施必须通过现有 M2 组件目录统一同步，保留明确类别，并参与状态、参数、能力、冲突、连接、资源、网络和镜像闭包校验。前端工具目录只展示工具类别，不能把基础设施误当成学生工具入口。

### 7.3 全部镜像完成可执行接入

- 14 个运行时都必须由各自 manifest 提供完整平台适配声明，并完成启动、工作区、链连接、原生部署/交易/查询/重置、自检和回收闭环；不得以长期 `onboarding` 代替实现。
- 12 个工具都必须能在兼容组合中执行核心能力。`fabric-explorer` 已改为平台自建的原生 `peer` CLI 浏览器；Fabric 组合必须显式声明 `CORE_PEER_ADDRESS` 连接和 `runtime-state` 只读安全域挂载,由运行时生成的组织身份提供最小权限连接,不得再以旧上游漏洞或缺配置作为永久禁用理由。
- 4 个容器判题器都必须提供私有执行 WorkloadSpec、自检样例、受控命令和真实下游评测契约；镜像存在或版本命令成功不算接入完成。

### 7.4 编译器完成全部发布前校验

连接图必须校验端点存在、协议匹配、配置绑定、访问范围、启动依赖环、同组端口/Service/DNS/路由唯一和 NetworkPolicy 最小放行；资源汇总必须在发布前校验租户与平台配额。任何失败均拒绝发布，不在运行时静默改名、改端口或降级。

### 7.5 前端冻结解除后的接入边界

前端只负责提交声明式组件、参数和连接，展示编译诊断、不可变摘要、预拉取、自检和运行状态；高级视图只读展示服务端编译结果。前端不得编辑镜像地址、digest、启动命令、安全上下文、Secret 或 NetworkPolicy，也不得为禁用组件保留绕过入口。

### 8.2 当前仍未完成的后端/镜像前置阻断

以下不是浏览器问题，解决前不能称为全功能落地，也不能开始宣称“只剩浏览器真实测试”:

1. **供应链证明需要按变更集合闭合**：`images/image-digests.lock` 的 56 条记录是完整发布基线；`deploy/config/chaimir.env` 与环境 `backend/.env` 中的 `PLATFORM_IMAGE_ATTESTATIONS_JSON` 当前 26 条是本环境已经完成 Trivy/Cosign/SBOM 证明的可调度子集。两者数量不要求相等，不能把本机已有镜像、正式 digest lock 或可变 tag 直接当作当前环境证明。对于本轮实际变更的镜像，必须按 `deploy/README.md` 的选择性刷新流程重新构建/推送、按候选 digest 回拉、完成安全门禁，再由 `image-attestations-generate.ps1` 生成证明并由 `images/sync-image-metadata.ps1` 晋升，同步写回正式锁、部署引用和两个环境证明文件；未完成该流程的镜像保持不可调度，不得手工补齐证明。
   - 仅修改 `manifest.yaml`、适配器声明或目录元数据时，不必虚构新的镜像 digest，但必须重新执行目录装配、自检和门禁映射校验；只要 Dockerfile、构建上下文或镜像内源码变化，就必须生成新 digest 并按同一供应链流程晋升。
2. **8 个 runtime 暂不开放平台原生动作，14 个 runtime 均待真实接入验收**：Cosmos、Aptos、Sui、NEAR、Solana、Substrate、Fabric、FISCO 当前按 `adapter_level: 1` 提供各自声明的 RPC、peer 或 REST 基础能力，可被工具、索引器、监听器和跨链组件通过 bindings 组合使用；只有实验明确调用 `deploy`、`tx`、`query` 时，组合编译器才拒绝缺失的动作能力。其余 6 个运行时的动作闭环也必须以各自 manifest 声明为准。镜像拉取、版本命令、查询或 Pod Ready 都不能单独判 PASS。
3. **判题器自检契约未闭合**：4 个容器判题器的 manifest `selftest.commands` 仍是版本命令；`platformJudgerResourceSpec` 未生成真实 `suite_ref`、`tenant_id`、`submitter_id`、`source_ref`、期望结果和下游测试资产，现有 `executeJudgerSelftest` 会按完整 fresh judge 路径拒绝或失败。已将未完成真实自检的容器判题器 seed 状态固定为 `disabled`，不得先出现在可选目录。
4. **FISCO 配置仍是运行期必需输入**：`images/runtime/fisco-bcos/entrypoint.sh` 只接受 `CHAIMIR_FISCO_CONFIG` 指向的 M2 生成并验证的 `config.ini`，当前 M2 初始化路径尚未生成并验证该配置；不能通过写死默认配置或跳过节点启动来规避。
5. **真实环境尚未复验**：本机 Docker Linux 引擎当前不可用，因此 14 个 runtime、12 个工具和 4 个判题器尚未完成本轮真实镜像启动、原生操作、工具核心操作、平台自检与真实下游评测。只读日志已定位为 Docker Desktop 在启动 Linux/WSL 引擎时执行 `wsl.exe -l -v --all` 超时（`DockerDesktop/Wsl/CommandTimedOut`），不是镜像不存在或供应链证明失败；当前会话无管理员权限重启 WSL 服务。静态 `go test`、manifest 校验、shell 语法和 Kustomize 只能证明代码/配置不明显损坏，不能替代业务通过。

## 九、前端接入 §6 契约时新发现的后端缺口(2026-08-24)

本节是前端按第六、八节把契约全量接完后暴露出的**新缺口**,不是重复第三节。
每条都写清「前端现在怎么处理」,以便后端补齐后能直接替换掉临时处理。

### 9.1 编排目录必须下发结构化绑定,前端不得猜测 `links`

`GET /sandbox/catalog` 的工具投影必须原样包含 `resource_spec.bindings`。
每个绑定提供稳定角色名、所需能力、目标端点、协议、启动前置和 `env:NAME` 注入键；
组合编译器只接受与这些声明逐项匹配的 `links`,不会按工具名称、生态标签或环境变量猜测连接。

- **前端现在的处理**:`links` 只原样带回上次编译结果并只读展示,不提供新建入口 ——
  凭猜测拼端点名与环境变量名等于伪造声明,违反 §7.5。
- **后端实现要求**:目录和 seed 已统一下发 `bindings`;编译器拒绝未声明的源端点、协议、启动前置或配置键。
  前端必须从绑定生成连接编辑器,能力提供者的选择仍由组合编译器按显式 runtime/组件和能力约束完成。

### 9.2 预拉取按「镜像 + 组合摘要」定位,但没有可用的组合摘要来源

`POST/GET /sandbox/runtimes/{id}/images/{img}/prepull` 现在要求 `composition_digest`,
且必须是**已发布**组合快照(`GetPublishedCompositionSnapshot`)。
但浏览器侧没有任何接口能列出「某镜像上有哪些已发布组合摘要」。

- **前端现在的处理**:平台运行时详情页保留预拉取入口,但摘要要管理员显式填入;
  页面文案说明预拉取按已发布组合执行。
- **需要后端补**:一个平台接口「按运行时/镜像列出已发布组合摘要(含所属实验或赛题的可读名)」。
  否则这条链路只能靠人从日志里抄摘要,不具备可运维性。

### 9.3 编排目录响应没有给运行时填 `capabilities`

`orchestrationCatalogResponse` 组装 `CatalogRuntimeResponse` 时没有传 `Capabilities`
(工具那一侧传了),故运行时的 `capabilities` 恒为零值。前端不依赖它,但这是响应与 DTO 声明不一致。

### 9.4 两个契约取值仍是裸字面量,契约门禁无法逐项对照

- 组件类别:编译器按 `"tool"` / `"infra"` 判定(`composition.go` 的 `expectedCategory`);
- 组件来源:按 `"explicit"` / `"auto"` 判定(`selection` 校验)。

两者都没有命名成 Go 常量,`scripts/audit/contract-enums.mjs` 无法把它们纳入字符串协议对照,
只能先登记为「待后端命名」。后端把它们提成命名常量(如 `SandboxComponentCategoryTool`、
`CompositionSelectionExplicit`)后,该脚本应把它们移入 `stringGroups` 做真实对照。

### 9.5 容器判题器无法从界面新建,只能由平台镜像目录同步登记

`parseJudgerExecutionSpec` 要求测试用例 / 静态扫描类判题器必须带非空 `execution_sidecars`,
而 sidecar 里含镜像地址、启动命令与安全上下文 —— 按 §7.5 前端不得编辑这些字段。

- **前端现在的处理**:表单不再提供 sidecar 的 JSON 编辑框;已有记录的 sidecar 只读带回并展示名称;
  新建这两类判题器时明确提示「需要先在平台镜像目录同步该判题器镜像」。
- **需要后端确认**:这是否即为预期路径(容器判题器只能由目录同步创建)。若是,请写入 §8.3;
  若否,需要给出一条不暴露镜像内部字段的登记方式。

### 9.6 题库实操题的环境声明已改由 `body.composition` 承载

竞赛解题与对抗环境现在只从 M5 锁定题目版本的 `body.composition` 读取
(`compositionFromProblem`),`battle_config` 不再携带任何环境字段。前端已跟改:

- 题库表单为竞赛题新增「这道题需要实操环境」开关与组合声明(写入 `body.composition`,
  不写 `access_profile` —— 由竞赛侧按解题/对抗场景写入);
- 赛题表单不再配运行时与工具,只配对抗规则,入场角色与回放方式按规则派生;
- 学生答题工作台按 `face.composition.runtimes[]` 判断是否有实操环境,
  起环境只提交 `{request_ref}`,不再拼装运行时与工具。

原先写在 `body.runtime_code` / `body.tools` 的字段后端已无任何消费方,前端已停止写入。
